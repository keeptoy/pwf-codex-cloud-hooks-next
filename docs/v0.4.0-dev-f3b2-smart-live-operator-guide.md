# v0.4.0-dev F3B2 smart Cloud 验收：新手操作手册

这是一份给维护者实际操作 F3B2 的大白话手册。它回答“先做什么、每个提交是什么、Cloud 里填什么、
提示词怎么发、脚本怎么跑、看到什么才算通过”。本轮所需的环境变量、setup/maintenance、workspace 前置检查、
production probe、evidence record 和停止条件都完整收录在这里；执行时不需要再打开另一份文档找缺失步骤。

活动 `task_plan.md` 仍控制当前授权和停止线。若仓库状态与本手册冻结值冲突，立即停止，不自行改脚本、创建计划、
移动 validation ref 或降低断言。

本手册最初放在 `docs/` 而不是 `docs/history/`，是因为 F3B2 执行时需要一份可直接运行的完整协议；`docs/history/`
只保存冻结摘要，不承载第二份脚本和 SHA 表。F3B2 现已闭合，本文件暂作为该次 frozen operator/evidence explanation
保留；F3B/F3C 收口时再统一决定退休或转为历史入口。

<a name="f3b2-one-minute-model"></a>

## 1. 一分钟理解这次验收

Phase 4 的 opt-in 不是给 Cloud 容器申请 root 权限，也不是让模型弹授权框。它验证的是：仓库里已经提交且经过
人审的 managed activation token，能否让只读 managed runtime 从默认 `legacy` 切到 `smart`；删掉 token 后，
能否可靠退回 `legacy`。

这次使用五个固定提交，分成两个互不混淆的身份：

- **runtime source HEAD**：决定安装哪一套 managed runtime；四轮都固定为同一个 markerless 提交。
- **workspace lifecycle HEAD**：决定本轮工作区里 `.mode` 和 activation token 是什么状态；四轮各不相同。

```text
RUNTIME_SOURCE (同一个 b37eea4...，负责构建和安装)
        |
        +---------------------------> 四轮 Cloud 环境

WORKSPACE lifecycle（只改变已提交的 planning state）
S_PREP -> S_ARM -> S_DISARM -> S_REARM
 legacy     smart      legacy       smart
```

脚本和提示词都要用，不能二选一：

1. Cloud environment 的 setup/maintenance 脚本先证明 exact runtime source、candidate ZIP、安装和 doctor，再在模型启动前
   完成 exact workspace HEAD/state preflight。
2. 第一条无工具提示词证明真实 Host 的 `SessionStart` / `UserPromptSubmit` Hook 确实注入。
3. 最后一条只读脚本重新核对 workspace identity/state，并证明 production `effective_profile`、doctor 和零 snapshot residue。
4. S_ARM 还要真实 Resume，证明恢复会话后仍是 smart。

提示词不能证明 hash 和安装现场；脚本也不能伪造真实 Host 在模型调用前注入的上下文，所以两类证据缺一不可。

<a name="f3b2-stage-meaning"></a>

## 2. 四个 S 版本分别干什么

| 顺序 | 固定 branch / commit | 相对上一步唯一变化 | 应有状态 | 大白话目的 |
|---|---|---|---|---|
| `S_PREP` | `validation/v0.4.0-dev-f3b2-smart-prep` / `a39dc66c755ec19bf29504dc0844de995c6cf67c` | 只新增 `.mode`，内容为 `inject-smart\n` | repository=`smart_prepared`；runtime=`legacy` | 先把 smart 意图准备好，但还没有最终开关；证明旧 `.mode` 单独存在不会偷偷激活 |
| `S_ARM` | `validation/v0.4.0-dev-f3b2-smart-arm` / `1058e704d5ab3496ab1a91a414c20c2e8fe58177` | 只新增 `.pwf-codex-managed` | repository=`smart_armed`；runtime=`smart` | 人审后的 activation-only commit 是真正 opt-in commit point |
| `S_DISARM` | `validation/v0.4.0-dev-f3b2-smart-disarm` / `c9275ba02073adb184cd73550c5b9f54c6f8178c` | 只删除 `.pwf-codex-managed` | repository=`smart_prepared`；runtime=`legacy` | 证明只删开关即可退出，残留 `.mode` 不能自己复活 smart |
| `S_REARM` | `validation/v0.4.0-dev-f3b2-smart-rearm` / `6dea2225812939f7a5f9893f2ab90782742a264c` | 只重新新增同内容 `.pwf-codex-managed` | repository=`smart_armed`；runtime=`smart` | 证明不重写计划、不扩大授权，也能显式重新启用 |

### 三层状态怎么读

脚本同时打印三个容易被误认为同义词的值。它们其实分别观察不同层：

| 字段 | 它回答的问题 | 证据来自哪里 |
|---|---|---|
| `WORKSPACE_STAGE` | “刚才做了哪一步；当前 checkout 是提交链的哪个节点？” | exact workspace HEAD 与第 6 节冻结的 stage map |
| `REPOSITORY_STATE` | “现在计划目录的 machine-state 文件组合是什么样？” | repository-only state validator 对 `.mode`、activation 等文件的结构判定 |
| `EFFECTIVE_PROFILE` | “production 最终实际选择并执行哪个 renderer/profile？” | 第 11 节真实 production probe JSON |

最容易困惑的是 `S_DISARM`：

```text
WORKSPACE_STAGE     = S_DISARM
REPOSITORY_STATE    = smart_prepared
EFFECTIVE_PROFILE   = legacy
```

大白话是：当前 checkout 已执行“删除 smart activation”这一步；`.mode` 仍表示计划已经准备好参与 smart 协议，所以仓库
结构仍叫 `smart_prepared`；但最终开关 `.pwf-codex-managed` 已不存在，因此 production 必须运行 `legacy`。这三个值不同
不是异常，而是证明“准备状态不能自行激活、删除 commit point 立即退出”的核心安全性质。`S_PREP` 也是同样的
`smart_prepared + legacy`；只有 `S_ARM` / `S_REARM` 的完整 `smart_armed` 才能得到 `smart`。

还要区分 expected 与 actual：setup/preflight 打印的 `PWF_F3_EXPECTED_EFFECTIVE_PROFILE` 只是本轮应有结果；第 11 节从
production probe JSON 读取的 `effective_profile` 才是实际结果。脚本先断言 actual 等于 expected，之后打印
`PWF_F3_EFFECTIVE_PROFILE`。没有 probe JSON 与该断言，不能根据 stage 名或文件外观自行宣布 profile PASS。

必须按表中顺序逐轮通过；前一轮失败就停止。不要 merge 这四个 validation branch，也不要把这些 machine state
合回 `0.4.0-dev`。

<a name="f3b2-hash-refresh-rule"></a>

## 3. 先回答：这份手册 commit 后，哪些值会变

| 对象 | 手册 commit 后是否变化 | 原因 |
|---|---|---|
| `0.4.0-dev` 当前 HEAD | **会** | 新增文档本身就是一个新 commit |
| frozen runtime source HEAD `b37eea4...` | **不会** | 它是已经独立冻结的 validation ref，不跟随开发分支移动 |
| `S_PREP/S_ARM/S_DISARM/S_REARM` 四个 HEAD | **不会** | 四个 validation refs 已经固定，手册不进入它们的提交链 |
| candidate ZIP SHA-256 `df6001...` | **不会** | Release contract 排除 `docs/`，文档不进入 ZIP |

所以，确认本手册后只需 commit 新文档并 push 新的 `0.4.0-dev`；**不要重建五个 validation refs**。

只有 production、contract、bundle、installer 或其他 Release ZIP 输入发生变化，才必须停止并重新冻结 runtime source、
重建 candidate、重算 SHA，并重新审查整条验证链。不能把“本次临时构建出来的新 SHA”直接当成新的 expected input。

<a name="f3b2-local-preflight"></a>

## 4. push 前在本地确认固定值

在仓库根目录运行下面的 PowerShell。它只读取 Git refs，并临时构建一个 ZIP 做交叉核对；expected 值来自已经审核的
活动计划，不是由这次构建自我批准。

```powershell
$ErrorActionPreference = 'Stop'

$expected = [ordered]@{
  'validation/v0.4.0-dev-f3b2-runtime-source' = 'b37eea4706fed8d4e764f824eb75a3820f31c9be'
  'validation/v0.4.0-dev-f3b2-smart-prep' = 'a39dc66c755ec19bf29504dc0844de995c6cf67c'
  'validation/v0.4.0-dev-f3b2-smart-arm' = '1058e704d5ab3496ab1a91a414c20c2e8fe58177'
  'validation/v0.4.0-dev-f3b2-smart-disarm' = 'c9275ba02073adb184cd73550c5b9f54c6f8178c'
  'validation/v0.4.0-dev-f3b2-smart-rearm' = '6dea2225812939f7a5f9893f2ab90782742a264c'
}

foreach ($entry in $expected.GetEnumerator()) {
  $actual = (git rev-parse $entry.Key).Trim()
  if ($LASTEXITCODE -ne 0 -or $actual -ne $entry.Value) {
    throw "ref mismatch: $($entry.Key): expected $($entry.Value), got $actual"
  }
  "PWF_F3_LOCAL_REF=$($entry.Key) HEAD=$actual"
}

$candidate = Join-Path ([System.IO.Path]::GetTempPath()) ("pwf-f3b2-" + [guid]::NewGuid() + '.zip')
try {
  python tools/build_release.py build --output $candidate
  if ($LASTEXITCODE -ne 0) { throw 'candidate build failed' }
  python tools/build_release.py check --archive $candidate
  if ($LASTEXITCODE -ne 0) { throw 'candidate check failed' }
  $actualSha = (Get-FileHash -Algorithm SHA256 -LiteralPath $candidate).Hash.ToLowerInvariant()
  $expectedSha = 'df60010402d1faf937d82a66007bd6a7d78f557b8da41a14ab283922c9a4494c'
  if ($actualSha -ne $expectedSha) {
    throw "candidate mismatch: expected $expectedSha, got $actualSha"
  }
  "PWF_F3_LOCAL_CANDIDATE_SHA256=$actualSha"
} finally {
  Remove-Item -LiteralPath $candidate -Force -ErrorAction SilentlyContinue
}
```

预期最后没有 exception，并打印五个固定 HEAD 和 candidate SHA。若值不同，停止；不要顺手把文档里的 expected
值改成实际值。

<a name="f3b2-push-and-remote-check"></a>

## 5. 维护者 push 与远端只读核对

本地文档 commit 完成后，由维护者 push 开发分支和五个 frozen refs。智能体/Cloud 模型不得代替维护者做这些远端写入。

```bash
git push origin 0.4.0-dev
git push origin validation/v0.4.0-dev-f3b2-runtime-source
git push origin validation/v0.4.0-dev-f3b2-smart-prep
git push origin validation/v0.4.0-dev-f3b2-smart-arm
git push origin validation/v0.4.0-dev-f3b2-smart-disarm
git push origin validation/v0.4.0-dev-f3b2-smart-rearm
```

然后只读检查远端。五行的第一列必须分别等于第 2 节固定值，第二列是对应的完整 ref 名：

```bash
git ls-remote --heads origin \
  refs/heads/validation/v0.4.0-dev-f3b2-runtime-source \
  refs/heads/validation/v0.4.0-dev-f3b2-smart-prep \
  refs/heads/validation/v0.4.0-dev-f3b2-smart-arm \
  refs/heads/validation/v0.4.0-dev-f3b2-smart-disarm \
  refs/heads/validation/v0.4.0-dev-f3b2-smart-rearm
```

push 后不得继续向这些 validation branches 增加 commit。任何 ref 漂移都会使已审核 DAG 失效，必须停止重审。

<a name="f3b2-cloud-environment"></a>

## 6. Cloud environment 到底填什么

GitHub 地址就是这个项目可被 Cloud `git fetch` 的仓库地址。当前仓库应填写：

```text
PWF_F3_RUNTIME_SOURCE_REPOSITORY=https://github.com/keeptoy/pwf-codex-cloud-hooks-next.git
PWF_F3_RUNTIME_SOURCE_HEAD=b37eea4706fed8d4e764f824eb75a3820f31c9be
PWF_F3_CANDIDATE_SHA256=df60010402d1faf937d82a66007bd6a7d78f557b8da41a14ab283922c9a4494c
PWF_F3_CODEX_HOME=/opt/codex
PWF_F3_MANAGED_REQUIREMENTS=/etc/codex/requirements.toml
PWF_F3_SKILL_ROOT=/root/.agents/skills/planning-with-files
```

配置步骤：

1. 打开这个 GitHub 仓库对应的 Codex Cloud environment 设置。
2. 在 environment variables 中逐项新增或覆盖上面六项；不要只把它们写在聊天提示词里。
3. 在 setup script 粘贴本节下面的完整 Bash block。
4. 在 maintenance script 再粘贴同一份完整 Bash block，确保两栏字节相同。
5. 保存环境；开始 stage 前重新打开核对六个值，没有 `<...>`、`OWNER`、moving branch 或旧 candidate SHA。

逐项解释：

- `PWF_F3_RUNTIME_SOURCE_REPOSITORY`：setup/maintenance 用来 fresh-fetch runtime source 的 Git 仓库，不是 stage branch 名。
- `PWF_F3_RUNTIME_SOURCE_HEAD`：`git rev-parse validation/v0.4.0-dev-f3b2-runtime-source` 得到的已冻结 commit，不能填
  `0.4.0-dev`、`main`、`latest` 或 Cloud 当前 checkout HEAD。
- `PWF_F3_CANDIDATE_SHA256`：第 4 节复算并与活动计划核对的 fixed candidate digest，不是让 Cloud 随机构建后自行接受的值。
- 后三项：当前这轮 Cloud 环境的 explicit install inputs；它们不是永久平台常量，环境事实改变就停止复核。

在 Cloud environment 的 **setup script** 和 **maintenance script** 两栏，分别原样复制下面这一整段 Bash。
两个栏位必须完全相同；六个 frozen inputs 放在 environment variables，不要改成 moving branch 或硬编码到脚本正文。

REPOSITORY_STATE="$(PLAN_DIR="$PLAN_DIR" PACKAGE_ROOT="$WORKSPACE_ROOT" node <<'NODE'

OpenAI Cloud environment 的 setup 与任务 agent shell 是不同 Bash session，临时 `export` 不会自然穿过去；缓存恢复时还可能
运行 maintenance。因此六个变量要放 environment 配置，而不是只在 setup 顶部临时导出。官方行为说明见
[Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment)。

如果仓库是 private，Cloud transaction 必须确实有权限按 HTTPS URL fetch 这个 exact commit。若 fetch 失败，只能
`STOP/INCOMPLETE`；不能退化为当前 checkout、moving branch 或 cache 中“看起来装过”的文件。

<a name="f3b2-placeholder-map"></a>

## 7. 计划由谁创建，以及本轮固定路径

**Cloud 不创建计划。** 本轮的计划在冻结 validation chain 之前已经由本地开发流程创建、审核并提交。
`S_PREP` checkout 本身已经包含：

```text
.planning/.active_plan
.planning/2026-08-14-phase-4-f3b2-smart-live/task_plan.md
.planning/2026-08-14-phase-4-f3b2-smart-live/findings.md
.planning/2026-08-14-phase-4-f3b2-smart-live/progress.md
.planning/2026-08-14-phase-4-f3b2-smart-live/.mode
```

`S_ARM` 只在此基础上增加 `.pwf-codex-managed`；`S_DISARM` 只删除它；`S_REARM` 只重新增加它。四个
Cloud tasks 都是读取已经提交的文件，不运行 init、writer、自动 commit 或“缺什么补什么”的提示词。

如果选择了正确 stage branch，Host Hook 在模型回答前就可以读取已提交计划。但注入正文不保证显示计划目录名，
所以第一条黑盒提示词只检查实际可见的 exact 计划标题与关键内容；`.active_plan` 是否精确指向 plan ID 由第 8 节 shell
前置检查证明。如果看不到计划正文，说明 checkout、Hook、安装或 resolver 有问题，应报告 `MISSING` 并停止；临时创建

## 9. Cloud 四轮执行顺序

每轮新建 Cloud task 时选择表中的 exact validation branch。模型开始做任何事情前，setup/maintenance 必须取得最终
`exit_code=0`，并打印：

```text
PWF_F3_CLOUD_RUNTIME_TRANSACTION_V1=PASS
PWF_F3_RUNTIME_SOURCE_HEAD=b37eea4706fed8d4e764f824eb75a3820f31c9be
PWF_F3_CANDIDATE_SHA256=df60010402d1faf937d82a66007bd6a7d78f557b8da41a14ab283922c9a4494c
PWF_F3_WORKSPACE_PREFLIGHT=PASS
PWF_F3_WORKSPACE_STAGE=<本轮 actual S_*>
PWF_F3_WORKSPACE_LIFECYCLE_HEAD=<本轮 exact HEAD>
```

推荐顺序：

1. **S_PREP cold Fresh**：reset environment cache，新任务选择 prep branch；验证 legacy。
2. **S_ARM cold Fresh**：再次 reset cache，新任务选择 arm branch；验证 startup smart、UserPromptSubmit smart。
3. **S_ARM real Resume**：恢复同一个 armed 会话；验证 `SessionStart source=resume`，仍为 smart。
4. **S_DISARM Fresh**：新任务选择 disarm branch；验证回到 legacy。
5. **S_REARM Fresh**：新任务选择 rearm branch；验证重新变为 smart。

这里有五次观察，是因为 `S_ARM` 同一个提交要测 Fresh 和 Resume 两条 Host 生命周期。cache 命中、未命中或不可观察只记录
`reset|hit|miss|unknown`，都不是正确性前提。

每个 Fresh stage 内部固定按这个次序执行：

1. 选择 exact validation branch，新建 task；需要 cold Fresh 的 stage 先 reset cache。
2. 等待第 6 节 setup/maintenance 完成 runtime transaction **和** workspace preflight；必须取得最终 `exit_code=0`
   及上述 exact 输出。否则停止，不给模型发送验收提示词。
3. 发送第 10.1 节第一条无工具提示词，保存真实 Host 注入。
4. 发送第二条提示词，只运行第 11 节最终校验脚本并等待它的最终 exit code；不再运行另一份 preflight。
5. 保存原始 stdout/stderr 与最终 exit code，按第 12 节生成并校验 evidence record。

## 12. 每轮怎样收证据

每轮至少保存：

- setup 或 maintenance 的最终 exit code、runtime source HEAD、candidate SHA 和 transaction PASS；
- 第一条回复中实际出现的 SessionStart/UserPromptSubmit canary 与 plan context；
- 当前 workspace `git rev-parse HEAD` 和 clean worktree；
- 第 11 节原始 `PROBE_JSON`，尤其是实际 `effective_profile` 与 `advisory`；
- doctor JSON、snapshot leftovers 和只读脚本最终 exit code；
- cache 事实：`reset|hit|miss|unknown`，不要猜；
- S_ARM Resume 中实际出现的 `SessionStart source=resume`。

把实际证据写入 disposable `/tmp/pwf-f3b2-<stage>.json`。JSON 必须严格使用以下字段，不多不少：

```json
{
  "schema_version": 1,
  "profile": "smart",
  "stage": "armed",
  "runtime_source_head": "b37eea4706fed8d4e764f824eb75a3820f31c9be",
  "candidate_sha256": "df60010402d1faf937d82a66007bd6a7d78f557b8da41a14ab283922c9a4494c",
  "workspace_lifecycle_head": "1058e704d5ab3496ab1a91a414c20c2e8fe58177",
  "worktree": "clean",
  "session_start_sources": ["startup", "resume"],
  "user_prompt_observed": true,
  "hook_context": "smart",
  "effective_profile": "smart",
  "advisory": null,
  "doctor_healthy": true,
  "snapshot_leftovers": 0,
  "cache_state": "reset",
  "final_exit_code": 0
}
```

上面只是 armed 字段形状示例，不是可以照抄的 PASS。必须用本轮实际 stdout/JSON/Git/Host 观察替换 stage、workspace
HEAD、session sources、hook/effective profile 和 cache state。然后在当前 stage checkout 执行：

下面整段是 **Bash 命令**；代码围栏标记为 `bash`。其中 `node <<'NODE' ... NODE` 是 Bash heredoc：Bash 启动
Node，并把中间的 JavaScript 交给 Node 执行。JavaScript 从当前 stage checkout 的
`tests/f3-lifecycle-helpers.js` 导入 `validateF3EvidenceRecord`。这个模块是 repository-only evidence helper，不是
production runtime，也不是启动完整 `node --test`；该函数直接用 Node assertions 检查 exact keys、stage/profile 关系、
40/64 位 identity、clean worktree、Host sources、doctor、零 residue 与最终 exit code。

```bash
PROJECT_ROOT="$(git rev-parse --show-toplevel)"
EVIDENCE_JSON="/tmp/pwf-f3b2-<replace-stage>.json"
EVIDENCE_JSON="$EVIDENCE_JSON" PACKAGE_ROOT="$PROJECT_ROOT" node <<'NODE'
const fs = require("node:fs");
const { validateF3EvidenceRecord } = require(
  process.env.PACKAGE_ROOT + "/tests/f3-lifecycle-helpers.js");
const record = JSON.parse(fs.readFileSync(process.env.EVIDENCE_JSON, "utf8"));
validateF3EvidenceRecord(record);
console.log("F3_EVIDENCE_RECORD_V1=PASS");
NODE
```

JSON 的 `stage` 依次是 `prepared`、`armed`、`disarmed`、`rearmed`。`hook_context` 不能靠文本外观猜：

- Host Hook 实际注入成功，且 probe 实际为 `legacy`，才记 `legacy`；
- Host Hook 实际注入成功，且 probe 实际为 `smart`，才记 `smart`；
- canary-only、缺失 Host 观察或 probe 不一致时，不得把 expected 值补成 PASS。

armed record 的 `session_start_sources` 在完成 Fresh + real Resume 后应为 `["startup", "resume"]`；其他 stage 只观察
Fresh 时写 `["startup"]`。所有值来自本轮实际 stdout/JSON/Git/最终 exit code，不从本手册复制“期待结果”冒充事实。

<a name="f3b2-stop-and-handoff"></a>

## 13. 什么时候停，什么时候算 F3B2 结束

任一情况立即停止并保留原始证据：

- Cloud checkout HEAD 不是本轮 exact stage commit，或 worktree 不干净；
- runtime transaction 不能 fresh-fetch exact source、candidate SHA 不同或最终 exit code 非零/未知；
- S_PREP/S_DISARM 实际不是 legacy，或 S_ARM/S_REARM 实际不是 smart；
- armed-invalid 静默回退 legacy、出现 partial plan、doctor 不健康或 snapshot residue 非零；
- Cloud 模型修改文件、commit、push、创建 PR、移动 branch，或试图“修复后继续”；
- 需要进入 autonomous、tamper、rollback 或修改 production 才能让本轮通过。

四个 stage record 与 S_ARM real Resume 都独立通过后，把原始输出和四份 JSON 回传本地复核。到这里最多只能判定
**F3B2 smart live chain PASS**；仍然停在 F3B3 autonomous、F3B4 汇总和 F3C rollback 之前，等待新的维护者授权。
