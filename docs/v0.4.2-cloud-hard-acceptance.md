# v0.4.2 Cloud hard acceptance

本文件是single-Discovery `v0.4.2`的Release operator guide。它编排Source/Candidate与Published Release两个独立通道，
但当前只完成Pre-run和candidate-readiness准入；Cloud、tag、public assets、Latest与final Post-run均未发生。

本版本没有新增product/runtime行为。要验证的是：文档治理delta已经收敛为一个可复现的`0.4.2`候选，exact v0.4.1
predecessor仍可安全进入未改变的installed runtime，最终公开下载字节与Source/Candidate实际验收字节一致。

执行关系：

```text
candidate-readiness checkpoint（已闭合）
  → C0 / Source-Candidate Cloud
  → C1 / channel checkpoint与维护者immutable publication
  → Published Release Cloud
  → Latest/postflight
  → role-window closeout checkpoint
  → C2 / final Post-run与programme closeout
```

本guide不创建standing Phase 9，不使用P9-A～F编号，也不授权维护者之外的远端写操作。

## 1. 定位与验收 claim

- 版本列车：`v0.4.2` documentation-governance Release closeout；不新增Product Phase。
- Discovery claim：Release/acceptance/history治理形成的仓库delta可以作为stable patch候选交付，同时保持v0.4.1已接受行为、
  exact predecessor admission与public download identity闭合。
- Source/Candidate证明final source、portable Linux suite、deterministic ZIP、override安装和真实Resume lifecycle。
- Published Release证明维护者发布的immutable bootstrap/ZIP默认下载链、Fresh startup与公开字节deep check。
- PASS不自动授权publication、Latest、下一Product Phase或任何production/runtime扩面。

## 3. 执行教程

### 3.1 本地与维护者push preflight

智能体完成完整本地回归、Release双构建和本地commit后，向维护者交接`SOURCE_CANDIDATE_HEAD`。维护者在本地执行：

```powershell
git status --short --branch
$expectedHead = (git rev-parse HEAD).Trim()
if (git status --porcelain) { throw "v0.4.2 Source/Candidate blocked: worktree is not clean" }
git push -u origin 0.4.2
$remoteLine = git ls-remote origin refs/heads/0.4.2
if (-not $remoteLine) { throw "v0.4.2 remote branch was not found" }
$remoteHead = ($remoteLine -split '\s+')[0]
if ($remoteHead -ne $expectedHead) { throw "v0.4.2 HEAD mismatch: local=$expectedHead remote=$remoteHead" }
"SOURCE_CANDIDATE_HEAD=$expectedHead"
```

远端branch写入由维护者负责。此时不得创建tag、Pre-release、上传资产或把zero-hash bootstrap当作公开安装入口。

### 3.2 Source/Candidate Cloud

在全新disposable Cloud environment选择已push的exact `0.4.2` checkout。每个新task都先附
[`Cloud task验收权限前缀`](cloud-hard-acceptance-template.md#cloud-task-acceptance-permission-prefix)，再按下表执行；
不得复制旧聊天或历史acceptance中的脚本。

| 顺序 | 操作 | 唯一协议来源 | 必须回传 |
|---|---|---|---|
| A | 新setup task执行4.1 | [`Source/Candidate setup`](cloud-hard-acceptance-template.md#source-candidate-setup) | 最终exit code、HEAD、portable Linux TAP、双ZIP identity、install/doctor与`PWF_SOURCE_CANDIDATE_SETUP=PASS` |
| B | A PASS后新task执行5.1 | [`post-install Resume`](cloud-hard-acceptance-template.md#blackbox-post-install-resume) | 原始回复与真实SessionStart source |
| C | B同task执行第6节 | [`canonical baseline`](cloud-hard-acceptance-template.md#blackbox-canonical-baseline) | exact plan ID与acknowledgment；唯一允许的workspace改动 |
| D | 同task执行第7节 | [`canonical context`](cloud-hard-acceptance-template.md#blackbox-canonical-context) | 八项原始观察 |
| E1/E2 | 同task执行8.1后，从UI Resume同一task执行8.2 | [`real Resume`](cloud-hard-acceptance-template.md#blackbox-real-resume) | acknowledgment、catch-up、tail、真实Resume source与顺序 |
| F | E2同一resumed task重新提取当前模板9.1 | [`Source/Candidate deep check`](cloud-hard-acceptance-template.md#source-candidate-deep-check) | 最终exit code、HEAD、doctor、inventory、policy、residue与`PWF_SC_POST_RESUME=PASS` |

A/F HEAD必须同时等于维护者交接的`SOURCE_CANDIDATE_HEAD`。C产生的`.planning` fixture不提交，通道完成后丢弃环境。

### 3.3 Source/Candidate通过后的停止点

维护者把完整原始证据交回后，智能体只核对并追加Source/Candidate channel checkpoint，创建C1
`SOURCE_CANDIDATE_CHECKPOINT_HEAD`。正式`v0.4.2` tag必须继续精确指向C0 `SOURCE_CANDIDATE_HEAD`，不能指向C1。

C1 push后才由维护者创建immutable Pre-release并上传最终ZIP与ZIP外bootstrap。公开资产形成后，本guide再追加exact public
identity，独立Fresh Cloud按模板[`Published Release setup`](cloud-hard-acceptance-template.md#published-release-setup)、
5.2、C～E与[`Published Release deep check`](cloud-hard-acceptance-template.md#published-release-deep-check)执行第二通道。

## 4. 证据与停止条件

共同硬停止以[`模板第2节`](cloud-hard-acceptance-template.md#acceptance-hard-stops)为准，并增加：

- production、runtime bundle、Host ABI、managed events或adapter-only policy相对v0.4.1发生非预期变化；
- transition不是exact v0.4.1 predecessor，或候选宣称支持未列入contract的旧installed state；
- CHANGELOG/ROADMAP/guide把未运行通道写成PASS，或provenance提前出现未发布v0.4.2身份；
- Source/Candidate开始前bootstrap已经含非zero默认ZIP SHA，或publication后重新打包却沿用原tag/资产身份；
- Cloud模型自动修改候选、commit、push、创建PR/Release或没有取得真实最终exit code。

维护者回传必须保存A/F完整stdout/stderr和最终exit code、portable suite摘要、ZIP entries/size/SHA、B～E原始回复、
doctor JSON、inventory/policy/residue，以及任何首次失败输出。失败后若环境或候选字节改变，必须Fresh重跑对应通道。
