# v0.3.3 Cloud hard acceptance

> 目的：为 pristine catch-up runtime successor 冻结可直接重放的 Source/Candidate Cloud 验收，以及未来
> Published Release 的独立消费模板。当前状态：R5_SC_PASS / PUBLICATION_PASS / R5_PR_IN_PROGRESS / R5_PR_F_PASS；本文已经证明
> exact tag、Release 与公开双资产成立，但尚不证明 R5-PR Cloud、GitHub Latest 或 rollback 晋级成立。
>
> 本手册继承 v0.3.2 已经跑通的双通道骨架，但按 v0.3.3-dev 的 current machine contracts 与实际 Cloud
> lifecycle 拆分 B-SC/B-PR，并替换 runtime、inventory 与 supply-chain 断言。任何历史数字、脚本或资产
> 身份都不能直接复制成当前 PASS。

## 0. 执行路线

v0.3.3 Source/Candidate 已由维护者确认全部 PASS，当前已授权 stable seal 与 immutable publication。
第二条通道的 publication gate 已关闭；现在可以在独立 Fresh Cloud 环境执行，结果仍为 PENDING_R5_PR。

| 顺序/通道 | 身份与用途 | 当前状态 |
|---|---|---|
| 第一步 R5-SC Source/Candidate | Cloud 选择开发/验证分支；PASS 绑定运行时记录的完整 commit，以及从该 checkout 双构建出的精确 ZIP；使用显式本地 HOOKS_URL/HOOKS_SHA256 override 安装 | PASS；开发身份与 Cloud 原始证据已冻结 |
| 第二步 R5-PR Published Release | 固定 immutable tag/source；从公开 Release URL 校验 bootstrap，让 bootstrap 用自身默认 URL/SHA 下载 ZIP，再独立重跑 B～F | IN_PROGRESS；10.2/F PASS，B-PR～E 与 immutable oracle pending |

分支只是运输入口，不是验收身份。R5-SC PASS 只属于当次输出的 RUNBOOK_HEAD、实际 ZIP 字节和独立
Cloud 环境；它不证明 tag 或公开 Release 成立。R5-PR PASS 只属于本节已经登记的 immutable tag、公开
bootstrap/ZIP 字节、filename、size、SHA 和默认下载链，不能由 workspace 中的同名文件代替。

两条通道不得共用容器、安装状态或 B～F 结果。planning scope、transcript 与任何 setup 残留同样不得
跨通道复用。正式顺序为：

1. 新建或 Reset cache 的 Node 22 Cloud 环境，environment setup script 保持为空；agent 启动并切到选定
   Source/Candidate checkout 后，在第一条任务提示中运行第 4 节 R5-SC 脚本。
2. 脚本必须输出 V033_DEV_SOURCE_CANDIDATE_SETUP=PASS；随后在同一已安装环境创建新 task，执行第 5.1 节
   B-SC，再依次执行第 6～9 节。安装发生在原始 startup 之后，因此 B-SC 验证 post-install Resume。
3. 保存完整原始输出并弃用该 Cloud 环境。任一步失败立即停止，不 repair 掩盖失败。
4. 只有 seal/publication gate 把第 10 节全部 placeholder 替换为经过复核的 immutable 值后，才在另一个
   Fresh Cloud environment setup 中执行 R5-PR bootstrap；首个 task 执行第 5.2 节 B-PR，再重跑 C～F。
5. 两条通道即使分别 PASS，也只回传证据；不自行 tag、发布、提升 Latest 或改变 rollback 角色。

安装脚本内的 direct adapter probe 或 doctor 只证明安装链静态健康，不是 Runtime 自动注入的黑盒证据。
R5-SC 的 post-install Resume、R5-PR 的 Fresh startup、UserPromptSubmit 与 real Resume 必须在各自规定的
agent/task lifecycle 中观察，不能把两种 SessionStart source 合并成一项要求。

## 2. 硬停止条件

遇到任一情况立即停止并保存完整输出：

- 工作树在 setup 前不干净，或无法记录完整 RUNBOOK_HEAD；
- Node major 不是 22，或目标 CODEX_HOME 已有 managed runtime；
- 冻结的 R5-SC development bootstrap 证据不再是 zero-hash + explicit override，或 sealed R5-PR bootstrap
  未精确绑定本节登记的 ZIP SHA；
- portable Linux suite 出现 fail/skip，或 publication-only oracle 混入 tagless R5-SC；
- 两次 ZIP 不逐字一致、entry count 不是 21、bootstrap 进入 ZIP，或 ZIP 含 patcher/overlay ledger；
- importer、pristine hash、helper allowlist/closure、Git mode 或 extracted replay 任一失败；
- global PWF Skill 不 pristine，Managed policy 不再 adapter-only，或 installed inventory 不是 exact current set；
- R5-SC 的 B-SC 缺少 Resume SessionStart/UserPromptSubmit canary，或 R5-PR 的 B-PR 缺少 startup
  SessionStart/UserPromptSubmit canary；
- canonical plan 未自动注入、出现 Phase 4 marker，或 canary/catch-up/plan 顺序不符合 current contract；
- real Resume 缺少 catch-up、tail marker、canonical plan，或 SessionStart source 仍是 startup；
- post-resume doctor 不健康、repairable、存在 error/blocker、inventory/hash/mode drift 或 snapshot residue；
- R5-PR placeholder 尚未全部替换，或者尝试使用 moving branch、latest、zero hash、本地 override或 workspace 工具。

失败后不得放宽断言、手工执行 Hook/runtime 拼接 PASS，也不得 repair 后继续计为同一次 PASS。产品或字节
修复后必须从对应通道的 Fresh setup 重新开始；任何公开资产变化都需要新身份、新 hash 和重新验收。
