# v0.5.0 Release Operator Guide

本文件是multi-Discovery `v0.5.0`列车的版本级Release operator guide；它不是新的Product Discovery Round，也不把
Phase 5.1、Phase 5.3或其各gate重新拼成一份巨型version acceptance。它编排Source/Candidate与Published Release两个
独立通道；Source/Candidate与Published Release已经分别在独立Cloud环境真实PASS，第一轮retirement review与C1已完成，
公开tag的metadata缺口也已在不改变peeled C0或双资产的前提下修复。维护者随后确认同一Release已晋级Latest且不再是
Pre-release；第二轮retirement、accepted/fallback轮转与C2现已闭合。

本次FULL Release要验证的是：Phase 5文档治理与`owned-plan` nonce/attestation exact-single-LF收紧可以作为同一
`v0.5.0`候选交付，同时保持legacy默认、显式opt-in、adapter-only policy、exact v0.4.4 predecessor admission、
deterministic ZIP和公开下载身份闭合。Phase 5.3 G1～G3的classifier/evidence-plan输出只解释为什么必须走FULL，不能
替代任何Cloud通道。

```text
candidate admission preflight（COMPLETE；只读、不删除）
  -> replacement C0 / Source-Candidate candidate（本地冻结并交接）
  -> Source/Candidate Cloud（PASS）
  -> source-candidate closeout retirement checkpoint（COMPLETE；全部KEEP）
  -> C1 / channel checkpoint与第一退役证据（本地状态写回）
  -> tag精确指向C0并完成immutable publication
  -> Published Release Cloud（PASS）
  -> guarded annotated-tag metadata repair（COMPLETE；peeled C0与双资产不变）
  -> GitHub Release Latest promotion confirmation（COMPLETE）
  -> role-window closeout checkpoint（COMPLETE）
  -> C2 / final Post-run与programme closeout（COMPLETE）
```

本guide不创建新Product Discovery Round，也不授权维护者之外的远端写操作。宏观顺序只读
[`ROADMAP`的Release四步与C0/C1/C2](../../ROADMAP.md#release-four-step-flow)和
[`ROADMAP`的两个retirement checkpoint](../../ROADMAP.md#version-train-two-retirement-reviews)；Latest判断只读
[`GitHub Release Latest promotion confirmation`](../../ROADMAP.md#github-release-latest-promotion-confirmation)。

## 1. 定位与验收 claim

- 版本列车：`v0.5.0` FULL Release candidate；继续归属已激活但尚未closeout的Product Phase 5。
- Product claim：nonce与attestation只接受exact单个LF结尾；缺失LF、CRLF、多余LF或尾随空白继续fail closed。
- 治理claim：Phase 5形成的authority、planning/history和Release risk-lane治理不进入Release ZIP或production trusted graph。
- Source/Candidate证明final source、portable Linux zero-skip suite、deterministic ZIP、override安装以及Fresh/UserPrompt/real Resume生命周期。
- Published Release证明immutable bootstrap/ZIP默认下载链、Fresh startup、公开字节deep check与role-window closeout。
- 任一PASS都不自动授权publication、Latest、Phase 5 closeout、下一Product Phase或新的Product/runtime扩面。

## 3. 执行教程

### 3.1 本地与维护者push preflight

智能体完成完整本地回归、Release双构建和C0 commit后交接`SOURCE_CANDIDATE_HEAD`。维护者执行：

```powershell
git status --short --branch
$expectedHead = (git rev-parse HEAD).Trim()
if (git status --porcelain) { throw "v0.5.0 Source/Candidate blocked: worktree is not clean" }
git push -u origin 0.5.0
$remoteLine = git ls-remote origin refs/heads/0.5.0
if (-not $remoteLine) { throw "v0.5.0 remote branch was not found" }
$remoteHead = ($remoteLine -split '\s+')[0]
if ($remoteHead -ne $expectedHead) { throw "v0.5.0 HEAD mismatch: local=$expectedHead remote=$remoteHead" }
"SOURCE_CANDIDATE_HEAD=$expectedHead"
```

远端写入由维护者负责。此时不得创建tag、Pre-release、上传资产或把zero-hash bootstrap当作公开安装入口。

### 3.2 Source/Candidate Cloud

在全新disposable Cloud environment选择已push的exact `0.5.0` checkout。每个新task先附
[`Cloud task验收权限前缀`](../cloud-hard-acceptance-template.md#cloud-task-acceptance-permission-prefix)，再按下表执行；不得复制旧仓库、
旧聊天或旧tag checkout中的脚本。

| 顺序 | 操作 | 唯一协议来源 | 必须回传 |
|---|---|---|---|
| A | 新setup task执行4.1 | [`Source/Candidate setup`](../cloud-hard-acceptance-template.md#source-candidate-setup) | 最终exit code、HEAD、portable Linux TAP（`fail=0`、`skipped=0`）、双ZIP identity、install/doctor与`PWF_SOURCE_CANDIDATE_SETUP=PASS` |
| B | A PASS后新task执行5.1 | [`post-install Resume`](../cloud-hard-acceptance-template.md#blackbox-post-install-resume) | 原始回复与真实SessionStart source |
| C | B同task执行第6节 | [`canonical baseline`](../cloud-hard-acceptance-template.md#blackbox-canonical-baseline) | exact plan ID与acknowledgment；唯一允许的workspace改动 |
| D | 同task执行第7节 | [`canonical context`](../cloud-hard-acceptance-template.md#blackbox-canonical-context) | 八项原始观察 |
| E1/E2 | 同task执行8.1后，从UI Resume同一task执行8.2 | [`real Resume`](../cloud-hard-acceptance-template.md#blackbox-real-resume) | acknowledgment、catch-up、tail、真实Resume source与顺序 |
| F | E2同一resumed task重新提取当前模板9.1 | [`Source/Candidate deep check`](../cloud-hard-acceptance-template.md#source-candidate-deep-check) | 最终exit code、HEAD、doctor、inventory、policy、residue与`PWF_SC_POST_RESUME=PASS` |

A/F HEAD必须等于交接的`SOURCE_CANDIDATE_HEAD`。C产生的`.planning` fixture不提交，通道完成后丢弃环境。

### 3.3 Source/Candidate通过后的停止点

维护者带回完整原始证据后，智能体核对真实PASS，再执行source-candidate closeout retirement checkpoint。第一轮只对
Release-excluded planning、临时教程和脚手架提出`RETIRE/MIGRATE/KEEP`；planning删除仍需维护者按
[`Planning生命周期`](../repository-governance-guide.md#planning-lifecycle)明确决定。随后把channel checkpoint与第一退役结论写回
C1 `SOURCE_CANDIDATE_CHECKPOINT_HEAD`。

维护者push C1后，正式`v0.5.0` annotated tag必须精确指向C0 `SOURCE_CANDIDATE_HEAD`，不能指向C1。具体命令只读根
[`Wiki`的“先给已通过的C0创建并推送正式tag”](../../Wiki.md#source-candidate-c0-tag-push)。若拟清退对象或PASS后改动会
改变package、contract、runtime、bootstrap、ZIP allowlist或其他C0 Release输入，必须形成新C0并重新运行Source/Candidate。

## 4. 证据与停止条件

共同硬停止以[`模板第2节`](../cloud-hard-acceptance-template.md#acceptance-hard-stops)为准，并增加：

- production、runtime bundle、Host ABI、managed events或adapter-only policy相对本C0发生非预期变化；
- transition不是exact v0.4.4 predecessor，或候选宣称支持未列入contract的旧installed state；
- exact-single-LF负向矩阵被弱化，或文档把G1～G3/本地/Windows证据写成stable C0 Cloud PASS；
- Source/Candidate前bootstrap含non-zero默认ZIP SHA，或publication后重新打包却沿用原tag/资产身份；
- Cloud模型修改候选、commit/push、创建PR/Release，或没有取得真实最终exit code。

维护者回传必须保留A/F完整stdout/stderr和exit code、portable suite摘要、ZIP entries/size/SHA、B～E原始回复、doctor JSON、
inventory/policy/residue及首次失败输出。失败后若环境或候选字节改变，必须Fresh重跑对应通道。
