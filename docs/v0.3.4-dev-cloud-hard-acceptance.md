# v0.3.4-dev Cloud hard acceptance

本文件是 v0.3.4-dev 的 Source/Candidate 执行入口，不复制稳定黑盒提示词，也不预填 commit、测试数量、
ZIP size/hash、PASS/PENDING ledger 或 Cloud 模型回复。稳定协议唯一来自
[`Cloud hard acceptance template`](cloud-hard-acceptance-template.md)；实际动态证据在运行后一次性回传并登记。

当前 Source/Candidate 的 Cloud hard acceptance 尚未开始。development bootstrap 继续使用 64 位 zero hash并
fail closed，只允许以当次 candidate ZIP 的 `file://` URL 与 SHA-256 显式 override；本入口不能证明 tag、
Published Release、Latest 或 rollback 身份。

## 1. 执行输入与边界

| 项目 | 本次输入/边界 |
|---|---|
| branch transport | 远端 `0.3.4-dev`；脚本必须自行输出完整 `RUNBOOK_HEAD`，分支名不是验收身份 |
| Cloud environment | 全新或 Reset cache；environment setup 保持为空；目标 managed runtime 必须不存在 |
| Node | 在 Cloud environment settings 中把预先选择的 major 写入 `PWF_ACCEPTANCE_NODE_MAJOR`；产品最低仍是 Node 18 |
| 安装通道 | 仅 Source/Candidate：agent startup 后从 source 双构建 ZIP，再以本地 override 安装 |
| Published Release | NOT AUTHORIZED |
| Stable seal/publication | NOT AUTHORIZED |
| Product Phase 4 | NOT AUTHORIZED |

exact current id/source inventory guard 必须继续阻止未准入 Phase 4 文件进入 bundle。不得在 Cloud 补造 tag/
remote，不得运行 publication-only oracle，不得把 direct adapter probe 或 doctor 当成 Runtime lifecycle 黑盒。

## 2. 本版本唯一架构增量

本次没有改变 B～E 可观察行为：events、canary、plan-first、可选 catch-up、planning context 与 Resume source
合同均保持不变。因此黑盒提示词必须直接使用模板，不得复制后加入版本号、阶段 marker 或预期 PASS。

需要额外证明的是 source/install authority 已收敛：

```text
upstream-manifest schema 2
  -> 固定 runtime bundle path + raw SHA
  -> importer / installer 严格解析同一 bundle inventory
  -> installed-manifest 保存安装快照
  -> doctor 比较当前 bundle authority、installed snapshot 与磁盘实际文件
```

模板的 Source/Candidate setup 已检查 schema 2 exact keys、退休 mirrors 不再出现、bundle 原始 SHA、Phase 4
负向准入与 portable negative suite；post-resume deep check 则要求 bundle-derived installed inventory、
`installed-manifest.runtime_files` 和磁盘实际 inventory 三者完全相等。旧 v0.3.3 脚本中读取
`manifest.managed_runtime.files` 的断言不得带入本版本。

## 3. 维护者执行顺序

1. 在 Cloud 选择远端 `0.3.4-dev`，确认 Fresh/Reset cache、空 environment setup，并配置
   `PWF_ACCEPTANCE_NODE_MAJOR`。
2. agent 启动后的第一条任务执行模板
   [`4.1 Source/Candidate setup`](cloud-hard-acceptance-template.md#source-candidate-setup)。必须得到脚本打印的
   `PWF_SOURCE_CANDIDATE_SETUP=PASS`，但不要把这行单独当成完整 Cloud PASS。
3. 在同一已安装环境创建新 task，原样发送模板
   [`5.1 post-install Resume`](cloud-hard-acceptance-template.md#blackbox-post-install-resume)。SessionStart 与
   UserPromptSubmit 必须观察到，SessionStart source 必须是真实 Resume source而不是 startup。
4. 在该 task 依次原样执行模板
   [`6 canonical baseline`](cloud-hard-acceptance-template.md#blackbox-canonical-baseline) 与
   [`7 canonical context`](cloud-hard-acceptance-template.md#blackbox-canonical-context)。
5. 原样执行模板 [`8 E1/E2 real Resume`](cloud-hard-acceptance-template.md#blackbox-real-resume)：E1 后离开 task，
   重新打开完全相同的 task，再把 E2 作为第一条消息发送。
6. E2 成功后执行模板
   [`9.1 Source/Candidate deep check`](cloud-hard-acceptance-template.md#source-candidate-deep-check)，确认 doctor、
   bundle authority、installed snapshot、实际 inventory、pristine Skill、adapter-only policy 与 snapshot residue。
7. 任一步失败立即按模板的
   [`共同硬停止条件`](cloud-hard-acceptance-template.md#acceptance-hard-stops) 保存第一次错误并停止；不得 repair
   后把同一次 run 记为成功。

## 4. 回传证据

请原样回传以下内容，不需要手工整理成状态表：

- Source setup 全部 stdout/stderr，包括完整 `RUNBOOK_HEAD`、portable suite 摘要、明确排除的 publication suite、
  两次 ZIP build/check、entry count、size、SHA 与 override 安装结果；
- B-SC、C、D、E1、E2 的每条原始模型回复，尤其是两次 SessionStart source、完整 canary、catch-up 报告、
  Unsynced messages 与 tail marker；
- 9.1 的 doctor JSON、`BUNDLE_INSTALLED_INVENTORY=AUTHORITATIVE`、installed inventory、adapter-only policy 与
  residue 输出；
- 若失败，回传失败步骤、第一次错误、环境是否 Fresh/Reset cache，并停止后续步骤。

证据字段的完整清单见模板
[`版本副本的证据写回`](cloud-hard-acceptance-template.md#acceptance-evidence-writeback)。Cloud 结果只关闭本次
Source/Candidate gate，不自动授权 Published Release、promotion、rollback 或 Product Phase 4。
