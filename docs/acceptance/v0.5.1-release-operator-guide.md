# v0.5.1 Release Operator Guide — G4 shadow

本guide承接Product Phase 5内的`v0.5.1`冻结验收guide保留改进，同时执行Phase 5.3 G4 shadow；不是新增Product Discovery
Round，也不是第三个Cloud通道。实际执行仍是现行FULL，分类器建议只用来对照同一批证据，不能省略B～E或提前启用G5。

声明范围为Source/Candidate、Published Release及G4对照。当前只交接第一通道；publication与后序通道要等真实第一通道PASS、
C1及维护者后续指示。宏观顺序只读[`Release四步`](../../ROADMAP.md#release-four-step-flow)和
[`两次retirement checkpoint`](../../ROADMAP.md#version-train-two-retirement-reviews)。本guide不授予远端写权限。

## 1. 定位与验收 claim

- 实际维护改进：版本级guide退出当前角色后保留原路径、冻结原文和证据，Acceptance README提供当前/历史导航；历史重放
  使用冻结源码与当时模板。不恢复已清退文件，不提前把accepted v0.5.0标为历史。
- G4 claim：exact低风险列车的V3建议覆盖FULL实际发现的相关风险，false-fast为0，Host/profile与资产身份一致，并取得可审计
  的耗时和人工往返对照。FULL成功不是自动的G4 PASS；遗漏或证据不足只能保持未闭合。
- 不改变runtime、installer、Host ABI、trusted graph、bundle inventory、bootstrap模板或双通道/两检查点/C0～C2规则。
- 尚未证明：本轮Cloud行为、公开资产身份、G4通过、实际精简流程收益、G5 enablement或Phase 5 closeout。

## 3. 执行教程

### 3.1 维护者同步与exact源码检查

本地handoff返回完整`SOURCE_CANDIDATE_HEAD`和单独的governance HEAD。维护者push当前`0.5.1`治理分支；Cloud必须选择handoff
的C0 commit，而不是默认使用更晚的branch HEAD。后续治理写回不等于C1；C1只能在第一通道真实PASS后创建。

每个Cloud task先附[`验收权限前缀`](../cloud-hard-acceptance-template.md#cloud-task-acceptance-permission-prefix)。在任何安装前，
核对`git rev-parse HEAD`等于handoff的完整C0，工作树clean，并记录当前OS、Node/Python版本及实际Host路径。不一致立即停止，
不在验收task内自行checkout、修复或commit。Node major未配置时，4.1按模板fail closed。

### 3.3 第一通道通过后的停止点

维护者带回完整证据后，核对exact C0/ZIP/profile与shadow清单覆盖，执行第一次真实retirement review并写C1。planning全部保持
KEEP，删除仍需明确决定；若改变任何C0 Release输入，旧PASS作废并重新冻结候选。随后停止等待publication指示，不把本通道
PASS当成G4最终结论。正式tag将来只能指向C0，不得指向C1或本guide的较新governance HEAD。

### 3.5 G4 shadow对照：实际FULL一次，建议清单逐项核对

projector生成的EOF block是全部advisory gate ID清单；以实际C0的V3 JSON为准，不手工删ID。每个ID对应一行实际证据：

| 对照字段 | 必须记录 |
|---|---|
| gate / identity | V3 gate ID、exact C0或public URL/SHA、channel/stage |
| coverage | SHARED、FULL_ONLY；实际raw evidence位置、最终exit code/Host观察 |
| relevance / omission | 与本次mechanic或identity是否相关及理由；unresolved不能写成无遗漏 |
| result | OBSERVED_PASS / OBSERVED_FAIL / NOT_RUN / UNRESOLVED；不预填PASS |

local、Linux、Source/Candidate、Published Release、retirement五个维度都须覆盖。变化mechanic负向由retention registry/hash/
snapshot-link tests证明；实际role exit时再核验v0.5.0原文/path/SHA与历史登记，不在验收前强行轮转。

同一operation供两个gate ID使用时只执行/计时一次，记录共享关系。建议未要求的B～E仍完整执行并归为FULL_ONLY行为证据。
若FULL_ONLY发现任何与本变化或低风险前提相关的问题，记advisory omission/false-fast并停止低风险结论；无法解释时保持
UNRESOLVED，不因为最后修复后绿色就把计数归零。installation/runtime observable变化立即升级。

profile记录每个通道实际OS、Node/Python版本、CODEX_HOME、skill root、requirements path、managed events及非敏感
environment/task标识；profile必须兼容且Node major一致，environment/task必须独立。源码/bundle/predecessor、owner
fingerprints、候选ZIP与公开ZIP必须绑定同一C0，bootstrap默认ZIP URL/SHA必须匹配已公开字节。不得记录secret。

#### 耗时与人工往返

维护者对每个stage保存实际开始/结束UTC、elapsed seconds、人工主动操作秒数、UI Resume次数、人工录入/复制字段数和handoff
次数；未测项明确`NOT_MEASURED`，不能填0。A/B/C/D/E1/E2/F分别记录；UI等待/排队/空闲与agent执行时间分开。步骤嵌套时
只累加互斥区间，避免将总耗时与子命令时间重复相加。

FULL总成本使用实际测量；shadow最低成本仅扣掉能独立归属FULL_ONLY的实测区间。共享的suite、build、安装、doctor不能
重复计入“节省”；counterfactual不是一次真正简化run的实测收益。人工字段比较同时记录generated block的5个checklist
fields、0个manual evidence fields、0份authority正文复制，以及本轮实际operator录入和往返；不把generated=0当成人工总成本0。

对照缺raw evidence、计时或operator comparison时G4继续开放；两通道FULL PASS也不能填G4 PASS。G5必须独立决策与授权。

## 4. 证据与停止条件

共同硬停止只读[`Cloud模板`](../cloud-hard-acceptance-template.md#acceptance-hard-stops)，另加：

- classifier lane不再为RELEASE_MECHANICS、unknown非空、closure不完整，或classifier/policy/projector与production自修改。
- C0、runtime fingerprint、accepted predecessor、Host/profile或公开字节与classification key不一致。
- 建议清单漏项、相关FULL_ONLY反例、无法解释的observables、计时/人工证据缺失或模型越权。
- 将本地Windows skip当Linux PASS，将模型摘要当最终exit code，或以不同source/repair后的局部PASS拼接通道。

异常保存第一次错误，在更严格FULL Fresh gate重新开始；无明确最终状态只记INCOMPLETE/UNKNOWN。本guide不预填Post-run。
