# v0.4.1-dev Cloud hard acceptance

本文件同时承担两件版本内的事：记录 `v0.4.1-dev` 兼容性安全修复的粗粒度验收状态，并给维护者一张
Source/Candidate Cloud 运行单。稳定脚本、B～E 提示词、停止条件和 evidence schema 仍只由
[`Cloud hard acceptance template`](cloud-hard-acceptance-template.md)维护；这里不复制第二份通用协议，
也不复制 `v0.4.0` 的历史结果。

| Gate | 状态 | 证据与边界 |
|---|---|---|
| Windows path-topology local implementation | `PASS` | junction parent、direct runtime junction、nested link 与非目录 component 均在 backup/mutation 前拒绝；unknown 普通内容仍可备份卸载 |
| Source/Candidate Linux/POSIX + Cloud | `CURRENT / CLOUD_ACCEPTANCE_PENDING` | 按[通用 Source/Candidate sequence](cloud-hard-acceptance-template.md#source-candidate-sequence)执行；真实 Linux、FIFO、Fresh/Resume 和 deep-check 证据尚未回传 |
| Seal / publication / Latest | `NOT_AUTHORIZED` | development bootstrap 保持 64 位 zero hash并 fail closed；本 gate 通过不会自动授权发布 |

<a name="v0-4-1-dev-plain-language-workflow"></a>

## 0. 大白话：这轮谁负责什么

这个项目已经进入标准化的 `v0.4.x` 迭代流程，不需要每次重新发明本地与 Cloud 的协作方式：

```text
智能体：本地修改 → 本地测试 → 写好这张 Cloud 运行单 → 创建本地 commit
维护者：审核本地结果 → push exact commit → 在 Cloud UI 手动创建/继续/Resume task
智能体：核对维护者带回的原始输出 → 回填 exact evidence → 创建下一本地 commit
```

默认情况下，智能体不代替维护者 push，也不代替维护者点击创建 Cloud task。只有维护者针对当前 gate 明确要求并授权，
才临时改变这一分工。Cloud 模型本身只执行验收：不得修代码、切 branch、commit、push 或创建 PR；一旦发现问题，
原样报告并停止。

<a name="v0-4-1-dev-one-minute-run"></a>

## 1. 一分钟理解本轮 Cloud 验收

本轮只跑 Source/Candidate，不跑 Published Release。要证明的不是“公开包已经发布”，而是：维护者刚 push 的 exact
`0.4.1` source 能在真实 Linux Cloud 中零 skip 通过，现场构建出的两个 ZIP 完全一致，candidate 安装后能完成
post-install Resume、canonical UserPrompt、real Resume 和 deep check；新增 FIFO/symlink 路径安全用例必须实际执行。

固定顺序是：

```text
维护者 push 并核对 remote HEAD
  → 同一全新 disposable Cloud environment：4.1 setup task
  → 新 task：5.1 B-SC
  → 同一 task：6 C → 7 D → 8.1 E1
  → 从 Cloud UI 重新打开同一 task：8.2 E2
  → 同一 resumed task：9.1 deep check
  → 保存全部原始输出并交回智能体
```

4.1 是在第一个 agent startup 之后安装 runtime，所以后续正确入口是模板 5.1 的 post-install Resume；不要改用
Published Release 专用的 4.2、5.2 或 9.2，也不要把 setup task 中的手工 probe 当作 Fresh/Resume 黑盒证据。

<a name="v0-4-1-dev-maintainer-preflight"></a>

## 2. 维护者 push 与 Cloud 前置检查

先在本地 `0.4.1` 工作区运行下面的 PowerShell。它只负责把已经验收的本地 commit 交给远端，并冻结 Cloud 必须选择的
exact HEAD；若工作树不干净或远端不一致，停止，不要开启正式 Cloud task。

~~~powershell
git status --short --branch
$expectedHead = (git rev-parse HEAD).Trim()
if (git status --porcelain) { throw "v0.4.1 Cloud push blocked: worktree is not clean" }
git push -u origin 0.4.1
$remoteLine = git ls-remote origin refs/heads/0.4.1
if (-not $remoteLine) { throw "v0.4.1 remote branch was not found" }
$remoteHead = ($remoteLine -split '\s+')[0]
if ($remoteHead -ne $expectedHead) {
  throw "v0.4.1 HEAD mismatch: local=$expectedHead remote=$remoteHead"
}
"PWF_V041_EXPECTED_HEAD=$expectedHead"
~~~

在 Codex Cloud 中新建一个可丢弃 environment，选择本仓库和 `0.4.1` branch。把该环境实际 Node major 以纯数字设置为
`PWF_ACCEPTANCE_NODE_MAJOR`。如果不知道数字，可先在独立 fact-only task 运行
`node -p "process.versions.node.split('.')[0]"`，记录后丢弃该 task；正式验收必须从新的 clean task 开始。

每个新 task 的第一条消息都先附模板的
[`Cloud task 验收权限前缀`](cloud-hard-acceptance-template.md#cloud-task-acceptance-permission-prefix)。
工具若只返回 `session_id`、`running` 或部分 stdout，继续轮询同一 session；没有最终 exit code 只能记
`INCOMPLETE/UNKNOWN`。

## 3. Source/Candidate Cloud 运行单

不要从旧聊天、`/tmp` 文件或 `v0.4.0` 手册复制脚本。每一步都重新打开当前 pushed checkout 中的稳定模板，按下表操作：

| 顺序 | 维护者在 Cloud 中的操作 | 唯一内容来源 | 必须保存 |
|---|---|---|---|
| A | 创建正式 setup task；先附 0.4 权限前缀，再让模型原样执行 4.1 唯一 Bash block | [`4.1 Source/Candidate setup`](cloud-hard-acceptance-template.md#source-candidate-setup) | 最终 exit code；`PWF_SC_RUNBOOK_HEAD`；Linux runner 原始 TAP；两次 ZIP build/check、entries/size/SHA；install/doctor/probe；`PWF_SOURCE_CANDIDATE_SETUP=PASS` |
| B | A PASS 后，在同一 environment 新建 task；先附 0.4 权限前缀，再原样发送 5.1 | [`5.1 B-SC post-install Resume`](cloud-hard-acceptance-template.md#blackbox-post-install-resume) | 模型完整原始回复；真实 SessionStart source 与 UserPromptSubmit |
| C | 在 B 的同一 task 原样发送第 6 节；该提示词会明确结束 B 的无工具/不读文件限制，并只开放 bounded planning read + apply_patch | [`C canonical baseline`](cloud-hard-acceptance-template.md#blackbox-canonical-baseline) | exact plan ID 与单行 acknowledgment；这是唯一允许的 workspace 改动 |
| D | 在同一 task 原样发送第 7 节 | [`D canonical context`](cloud-hard-acceptance-template.md#blackbox-canonical-context) | 八项 OBSERVED/NOT_OBSERVED 原始回复 |
| E1 | 在同一 task 原样发送 8.1；收到精确 acknowledgment 后离开 task | [`E1 long tail`](cloud-hard-acceptance-template.md#blackbox-real-resume) | 精确 acknowledgment；不得继续修改 planning |
| E2 | 从 Cloud UI 重新打开 E1 的完全相同 task，第一条消息原样发送 8.2 | [`E2 real Resume`](cloud-hard-acceptance-template.md#blackbox-real-resume) | catch-up 原文、全部 canary、真实 resume source、tail 与顺序观察 |
| F | E2 完成后，在同一 resumed task 从当前 checkout 重新提取并执行 9.1 | [`9.1 Source/Candidate deep check`](cloud-hard-acceptance-template.md#source-candidate-deep-check) | 最终 exit code；HEAD、worktree、doctor、contract/inventory、policy、residue 与最终 PASS marker |

A 的 `PWF_SC_RUNBOOK_HEAD` 和 F 的 deep-check HEAD 都必须等于第 2 节的 `PWF_V041_EXPECTED_HEAD`。C 段会创建 disposable
`.planning` fixture；不要提交它，验收完成后直接丢弃整个 Cloud environment。

<a name="v0-4-1-dev-path-safety-delta"></a>

## 4. Path-safety acceptance delta

本版本新增 installer 路径拓扑边界：`hooks` parent、runtime root 或 runtime 内部 entry 若为 symlink、junction 或
special path，install、repair 与 uninstall 都必须在 backup 和任何 shared/runtime mutation 前 fail closed。uninstall
对 unknown 普通文件/目录的 recovery/cleanup 合同保持不变。

本增量由 4.1 自动发现的 portable installer tests 与 published round-trip transition oracle 验证。Linux runner 的原始
TAP 必须明确显示下列行为通过，并且整套 runner 为 0 fail、0 skip：

- linked hooks parent 在 install/uninstall 前拒绝；
- linked runtime root 与 nested runtime link 在 uninstall 前拒绝；
- nested FIFO 在 backup/mutation 前以 `BLOCKED_UNSAFE_RUNTIME_PATH` 拒绝；
- unknown regular file/directory 仍成功备份并卸载。

B、D、E 黑盒提示词、Host ABI、adapter-only policy 与 runtime dispatch 均未改变，原样复用稳定模板。C 只补充了
B→C 权限交接：明确结束 B 的单次无工具/不读文件观察限制，并仅开放 canonical planning fixture 所需的 bounded read
与 apply_patch；canonical 内容、预期 acknowledgment 和 production behavior 均不变。Windows 本地 SKIP 只证明测试被
正确分流，不能替代上述 Linux FIFO PASS。

<a name="v0-4-1-dev-pass-stop-and-return"></a>

## 5. PASS、停止条件和结果回传

只有以下条件全部满足，本轮才进入 evidence writeback：

- remote、4.1 与 9.1 三处 HEAD 都等于同一个 40 位 exact commit，setup 前 source worktree clean；
- 4.1 最终 exit code 为 0，Linux portable suite 为 0 fail、0 skip，FIFO/symlink/unknown-regular 用例实际 PASS；
- 两次 candidate ZIP 逐字一致，entry/size/SHA、override install、doctor 和 adapter probes 全部有原始输出；
- 5.1、6、7、8.1、8.2 按固定 task 关系完成，8.2 真实观察到 resume，而不是新 startup 或模型推断；
- 9.1 最终 exit code 为 0，doctor healthy，manifest-routed inventory 与 adapter-only policy 正确，snapshot residue 为 0；
- 除 C 段 canonical `.planning` fixture 外没有 workspace 改动，没有自动修复、commit、push、PR 或 ref mutation。

任何 HEAD/环境/测试/ZIP/Host/deep-check 不一致都立即停止，并保存第一次错误。产品或教程缺陷修复后从新的 Fresh
environment 重跑；异步命令没有最终 exit code 时只报 `INCOMPLETE/UNKNOWN`，不能把部分输出判成 PASS/FAIL。

维护者回传时请保留：第 2 节 exact HEAD、A 与 F 的完整 stdout/stderr 和最终 exit code、Linux TAP、ZIP identity、B～E
每条原始提示词与原始回复，以及任何首次失败输出。智能体核对后才把 exact evidence 和最终 PASS 写回本文件；当前不得
预填 Cloud commit、ZIP SHA 或 PASS marker，也不得自动进入 seal/publication。

当前结论：`LOCAL_PATH_SAFETY_PASS / SOURCE_CANDIDATE_CLOUD_PENDING / RELEASE_NOT_AUTHORIZED`。
