# v0.4.0-dev F3C disarm-first rollback：独立操作手册

本文是 F3C2/F3C3 真实 Cloud 验收的完整、独立入口，同时保存 F3C1 repository/Linux no-live 协议。
操作者不需要拼接 F3B2/F3B3 手册。操作方法与当前 programme 状态刻意分离：实际进度只看文末带日期的 status、
`ROADMAP.md` 和活动 task plan；历史 pre-run记录不代表当前 gate仍未执行。

<a name="f3c-section-map"></a>

## 0. 先看清自己在执行哪个 gate

不要把第 3～10 节理解成“一次从头跑到底”的单个测试。它们分属不同 gate：

| 手册部分 | 属于哪个 gate | 大白话作用 | 是否改动 Cloud installed runtime |
|---|---|---|---|
| 第 3 节 | F3C1 | 在 ref-aware Linux clone 中证明 rollback 协议、旧版本身份和两类 runtime-only 复活风险 | 否；只使用 disposable fixture |
| 第 4～9 节 | F3C2/F3C3 | 在真实 Cloud 中分别执行 smart/autonomous rollback 与 recovery，并收集 Host、doctor 和 evidence | 是；会执行 current install/uninstall、v0.3.5 clean install和 current recovery |
| 第 10 节 | 所有 live gate | 规定什么情况必须停、每个 gate通过后交给谁 | 否；它是规则，不是独立测试 |

第 3 节通过不自动授权第 4～9 节；F3C2通过也不自动授权 F3C3。每个 live gate都必须以活动 task plan和维护者授权为准，
并在本节规定的边界停止。文末带日期的记录只证明对应时点已经发生的验收，不会扩大下一 gate权限。

唯一支持链是：

```text
committed disarm + clean worktree
  → current-owned uninstall
  → immutable v0.3.5 clean install
  → current exact predecessor recovery
```

禁止让 v0.3.5 直接覆盖 current，禁止 armed/runtime-only rollback，禁止 installer 删除 workspace token，也禁止
根据 cache、stage 名或模型口述猜 installed role/profile。

<a name="f3c-one-minute-model"></a>

## 1. 一分钟理解四轮验收

smart 和 autonomous 各跑两轮：

| Stage | Workspace | 最终 installed role | 实际 profile | 要证明什么 |
|---|---|---|---|---|
| `S_ROLLBACK` | smart disarm | accepted `v0.3.5` | legacy | current 能先安全卸载，旧版只能 clean install |
| `S_RECOVER` | 同一 smart disarm | current `0.4.0-dev` | legacy | exact accepted predecessor 能正向迁回 current，token 不复活 |
| `A_ROLLBACK` | autonomous disarm | accepted `v0.3.5` | legacy | mode/nonce/attestation 保留但 inert，旧版只得到 legacy snapshot |
| `A_RECOVER` | 同一 autonomous disarm | current `0.4.0-dev` | legacy | current 恢复后 activation 仍不存在，autonomous 不复活 |

<a name="f3c2-smart-live-walkthrough"></a>

### F3C2 smart live 怎么跑

F3C2 smart live由下面两轮组成。两轮必须是两个全新 Cloud task，不能共享 workspace、shell 或 cache来证明身份。

`S_ROLLBACK` 回答“能不能安全退回 accepted”：

1. 从 smart exact disarm HEAD `c9275ba02073adb184cd73550c5b9f54c6f8178c` 创建全新 Cloud task。
2. transaction先安装并验证 current，再由 current installer卸载 current。
3. clean-install immutable `v0.3.5`，最终必须是 `installed_role=accepted`、`installed_version=0.3.5`。
4. Fresh、real Resume与 production probe都必须证明 legacy context；`.pwf-codex-managed` 继续不存在，smart 不得复活。
5. 生成并校验一份 `stage=rollback` evidence，然后停止该 task。

`S_RECOVER` 回答“退回以后能不能沿唯一准入路线恢复 current”：

1. 从同一个 smart exact disarm HEAD另建全新 Cloud task，不复用 `S_ROLLBACK` 容器。
2. transaction先完成 current-owned uninstall与 immutable `v0.3.5` clean install，再由 exact current candidate正向恢复。
3. 最终必须是 `installed_role=current`、`installed_version=0.4.0-dev`；workspace仍已 disarm，所以实际 profile仍必须是 legacy。
4. Fresh、real Resume、production probe、doctor与 residue全部通过后，生成并校验一份 `stage=recovered` evidence。
5. 停止并回传两份 smart evidence；不得继续跑 `A_ROLLBACK` 或 `A_RECOVER`。

<a name="f3c3-autonomous-live-walkthrough"></a>

### F3C3 autonomous live 怎么跑

F3C3 autonomous live同样由两个互相隔离的全新 Cloud task组成。它不再重复证明 smart，而是专门证明
autonomous disarm留下的准备态不会被 accepted旧 runtime或恢复后的 current runtime误当成已激活状态。

两轮都从 autonomous exact disarm HEAD `98b6f138497af244563541ec655a1111198f0c36` 开始。该 HEAD 应当保留：

- `.mode=autonomous`；
- 合法的 `.nonce`；
- 与当前 `task_plan.md` 精确匹配的 `.attestation`；
- zero-ledger state，即没有任何 ledger 文件；
- 不存在 activation commit point `.pwf-codex-managed`。

这些文件表达的是“autonomous 已准备、但尚未激活”。它们允许留在仓库中，但必须始终 inert；transaction、installer
和 production runtime都不得擅自创建、删除、修复或改写这些 workspace intent files。

`A_ROLLBACK` 回答“退到旧 runtime以后，autonomous 准备态会不会被误摄取”：

1. 从上述 exact HEAD创建全新 Cloud task，不复用任何 smart task、workspace、shell 或 cache。
2. transaction先验证并卸载 current，再 clean-install immutable `v0.3.5`。
3. 最终必须是 `installed_role=accepted`、`installed_version=0.3.5`、`repository_state=autonomous_prepared`；
   activation仍不存在，实际 effective profile必须是 legacy。
4. Fresh、real Resume和 production probe都应看到 legacy delimiter与 `=== recent progress ===`；不得看到 nonce delimiter、
   `Plan-SHA256:`、`=== ledger summary ===`、`=== RUN LEDGER ===` 或 `entries: 0`。这证明旧 runtime没有摄取
   nonce、attestation或 zero-ledger准备态。
5. 生成并校验一份 `profile=autonomous`、`stage=rollback` evidence，然后停止该 task；先复核证据，再决定是否授权下一轮。

`A_RECOVER` 回答“经过 accepted predecessor恢复 current以后，autonomous 会不会复活”：

1. 从同一个 exact HEAD另建全新 Cloud task，不复用 `A_ROLLBACK` 容器。
2. transaction先完成 current-owned uninstall与 immutable `v0.3.5` clean install，再由 exact current candidate正向恢复。
3. 最终必须是 `installed_role=current`、`installed_version=0.4.0-dev`、`repository_state=autonomous_prepared`；
   activation仍不存在，实际 effective profile仍必须是 legacy。
4. Fresh、real Resume和 production probe仍应只出现 legacy delimiter与 recent progress；不得出现任何 autonomous renderer
   标记、ledger summary或 autonomous profile。这证明 current恢复后没有把 prepared state当成 activation，也没有复活 autonomous。
5. 生成并校验一份 `profile=autonomous`、`stage=recovered` evidence，然后停止；不得自动进入 F3C4。

每一轮只有下面这一种操作顺序；第 6 节是这条顺序的检查表，不是另一段需要单独运行的脚本：

```text
第 4 节设置本轮环境变量
  → 第 5 节执行 installed-state transaction，并等到明确 exit_code=0
  → 第 7 节做 Fresh 无工具观察
  → real Resume同一 task，再做无工具观察
  → 第 8 节运行唯一只读 verifier，并等到明确 exit_code=0
  → 第 9 节生成、校验本轮 evidence JSON
  → 停止本轮 task
```

三层事实仍要分开：`WORKSPACE_STAGE` 是本轮做什么，`INSTALLED_ROLE` 是最终装了谁，`EFFECTIVE_PROFILE`
是 installed production 实际选择什么。`A_ROLLBACK` 可以同时是 autonomous prepared、accepted installed、legacy effective；
这三项不矛盾。

<a name="f3c-no-live-gate"></a>

## 3. F3C1 repository/Linux no-live gate

第 3 节必须在 **ref-aware Linux checkout** 运行。这里的“ref-aware”不是“当前目录里能看到旧 commit内容”就够了，
而是当前 Git object database中必须同时存在并可解析 `v0.3.5`、`v0.3.4` 两个 tag及其 source objects。

原因很具体：下面的测试文件来自当前 `0.4.0-dev` checkout；两个旧 tag并不提供第 3 节脚本。当前测试会用
`git rev-parse --verify <tag>^{commit}` 校验发布 tag指向，再用 `git archive`/`git show` 从对应历史 source重建旧 package和
runtime。第 3 节脚本不会自行联网补 tag。Cloud 默认 checkout若只有当前 branch/commit，即使文件内容完整，也可能因缺 tag
在测试真正开始前失败；这属于 checkout prerequisite failure，不是产品失败。

<a name="f3c-ref-aware-checkout"></a>

### 3.1 最稳妥的完整 clone 与前置核对

在 disposable `/tmp` 中完整 clone，不使用 `--depth`，再 checkout 已接受的 F3C1 exact source：

```bash
set -Eeuo pipefail

F3C1_CHECK_ROOT="$(mktemp -d /tmp/pwf-f3c-ref-aware.XXXXXX)"
git clone https://github.com/keeptoy/pwf-codex-cloud-hooks-next.git "$F3C1_CHECK_ROOT/repo"
git -C "$F3C1_CHECK_ROOT/repo" checkout --detach cdc4a9eba7e7f1f2545723829ed1a6b4c76cb48b

test "$(git -C "$F3C1_CHECK_ROOT/repo" rev-parse HEAD)" = \
  cdc4a9eba7e7f1f2545723829ed1a6b4c76cb48b
test "$(git -C "$F3C1_CHECK_ROOT/repo" rev-parse --verify 'v0.3.5^{commit}')" = \
  5d01b55890c1da2a5088e2b991b152a9fb1c3f87
test "$(git -C "$F3C1_CHECK_ROOT/repo" rev-parse --verify 'v0.3.4^{commit}')" = \
  59a999f705701ec67463649e9424f3d059863c81

cd "$F3C1_CHECK_ROOT/repo"
printf 'PWF_F3C1_REF_AWARE_PREFLIGHT=PASS\n'
```

如果现有 checkout 上述三项本来就能通过，可以直接使用；不要在来源不明的工作目录里手工创建同名 tag来伪造前置条件。
完整 clone下载的是 Git 历史 objects和 tag refs，不是从旧 tag中寻找第 3 节脚本，也不等于安装旧版 runtime。

前置核对通过后，在同一个 checkout 运行：

```bash
set -Eeuo pipefail
node --test --test-reporter=tap \
  tests/f3c-rollback-protocol.test.js \
  tests/published-release-oracles.test.js
```

必须得到最终 `exit_code=0`。`f3c-rollback-protocol.test.js` 的 smart/autonomous runtime-only revival 两项在 Linux
必须实际执行，不得 skip：它们证明未 disarm 时，旧 runtime 临时只呈现 legacy，但 unchanged activation 在 current
runtime 回来后会重新激活。publication oracle 另外证明旧 installer direct-over-current 在 backup/write 前拒绝，且
runtime、requirements、backup inventory 完全不变。

## 4. Cloud environment 变量

四轮使用同一份环境配置，只替换 `PWF_F3C_STAGE`：

```text
PWF_F3C_SOURCE_REPOSITORY=https://github.com/keeptoy/pwf-codex-cloud-hooks-next.git
PWF_F3C_PROTOCOL_SOURCE_HEAD=12a359096ab1e376014476b77a6b0833a7a90b2e
PWF_F3C_CURRENT_CANDIDATE_SHA256=df60010402d1faf937d82a66007bd6a7d78f557b8da41a14ab283922c9a4494c
PWF_F3C_ACCEPTED_ZIP_URL=https://github.com/keeptoy/pwf-codex-cloud-hooks-next/releases/download/v0.3.5/pwf-codex-cloud-hooks-v0.3.5.zip
PWF_F3C_ACCEPTED_ZIP_SHA256=7d351cfe0eaa60e93bc279645ed3f480dc9e83efdff1c6abf13c14d84c286f0b
PWF_F3C_CODEX_HOME=/opt/codex
PWF_F3C_MANAGED_REQUIREMENTS=/etc/codex/requirements.toml
PWF_F3C_SKILL_ROOT=/root/.agents/skills/planning-with-files
PWF_F3C_STAGE=S_ROLLBACK
```

`PWF_F3C_STAGE` 依次改为 `S_ROLLBACK`、`S_RECOVER`、`A_ROLLBACK`、`A_RECOVER`。每轮从对应 exact
disarm checkout 新建 task；不要让 Cloud 模型 checkout、commit、push、PR 或自动修复。

<a name="f3c-transaction"></a>

## 5. Setup 与 maintenance 共用的唯一 transaction

把下面同一 Bash block 原样放入 setup script 和 maintenance script。它先验证 workspace 已 committed disarm，再从
exact protocol source安装并校验 pristine `planning-with-files v3.8.2` Skill、构建 current ZIP、下载并校验 immutable
accepted ZIP，最后按 stage执行 transaction。`PWF_F3C_SKILL_ROOT` 只是安装目标，不会仅因设置变量而自动出现 Skill；
Skill bootstrap必须包含在本 block中，不能依赖某个旧 task碰巧已经安装。

```bash
set -Eeuo pipefail

: "${PWF_F3C_SOURCE_REPOSITORY:?missing source repository}"
: "${PWF_F3C_PROTOCOL_SOURCE_HEAD:?missing protocol source HEAD}"
: "${PWF_F3C_CURRENT_CANDIDATE_SHA256:?missing current candidate SHA-256}"
: "${PWF_F3C_ACCEPTED_ZIP_URL:?missing accepted ZIP URL}"
: "${PWF_F3C_ACCEPTED_ZIP_SHA256:?missing accepted ZIP SHA-256}"
: "${PWF_F3C_CODEX_HOME:?missing CODEX_HOME}"
: "${PWF_F3C_MANAGED_REQUIREMENTS:?missing managed requirements path}"
: "${PWF_F3C_SKILL_ROOT:?missing Skill root}"
: "${PWF_F3C_STAGE:?missing F3C stage}"

PROJECT_ROOT="$(git rev-parse --show-toplevel)"

case "$PWF_F3C_STAGE" in
  S_ROLLBACK)
    PROFILE=smart; PLAN_ID='2026-08-14-phase-4-f3b2-smart-live'
    EXPECTED_WORKSPACE_HEAD='c9275ba02073adb184cd73550c5b9f54c6f8178c'
    EXPECTED_REPOSITORY_STATE=smart_prepared; FINAL_ROLE=accepted
    ;;
  S_RECOVER)
    PROFILE=smart; PLAN_ID='2026-08-14-phase-4-f3b2-smart-live'
    EXPECTED_WORKSPACE_HEAD='c9275ba02073adb184cd73550c5b9f54c6f8178c'
    EXPECTED_REPOSITORY_STATE=smart_prepared; FINAL_ROLE=current
    ;;
  A_ROLLBACK)
    PROFILE=autonomous; PLAN_ID='2026-08-16-phase-4-f3b3-autonomous-materialization'
    EXPECTED_WORKSPACE_HEAD='98b6f138497af244563541ec655a1111198f0c36'
    EXPECTED_REPOSITORY_STATE=autonomous_prepared; FINAL_ROLE=accepted
    ;;
  A_RECOVER)
    PROFILE=autonomous; PLAN_ID='2026-08-16-phase-4-f3b3-autonomous-materialization'
    EXPECTED_WORKSPACE_HEAD='98b6f138497af244563541ec655a1111198f0c36'
    EXPECTED_REPOSITORY_STATE=autonomous_prepared; FINAL_ROLE=current
    ;;
  *) printf 'unknown PWF_F3C_STAGE=%s\n' "$PWF_F3C_STAGE" >&2; exit 1 ;;
esac

test "$PWF_F3C_PROTOCOL_SOURCE_HEAD" = "$EXPECTED_PROTOCOL_HEAD"
test "$PWF_F3C_CURRENT_CANDIDATE_SHA256" = "$EXPECTED_CURRENT_SHA"
test "$PWF_F3C_ACCEPTED_ZIP_SHA256" = "$EXPECTED_ACCEPTED_SHA"
test "$(git -C "$PROJECT_ROOT" rev-parse HEAD)" = "$EXPECTED_WORKSPACE_HEAD"
test -z "$(git -C "$PROJECT_ROOT" status --porcelain=v1 --untracked-files=all)"
PLAN_DIR="$PROJECT_ROOT/.planning/$PLAN_ID"
test -d "$PLAN_DIR"
test ! -e "$PLAN_DIR/.pwf-codex-managed"

TRANSACTION_ROOT="${TMPDIR:-/tmp}/pwf-f3c-transaction"

CURRENT_EXTRACTED="$TRANSACTION_ROOT/current"
ACCEPTED_ZIP="$TRANSACTION_ROOT/accepted.zip"
ACCEPTED_EXTRACTED="$TRANSACTION_ROOT/accepted"

git init -q "$SOURCE_ROOT"

test -f "$SKILL_BOOTSTRAP"
bash -n "$SKILL_BOOTSTRAP"
CODEX_HOME="$PWF_F3C_CODEX_HOME" \
PLANNING_WITH_FILES_ROOT="$PWF_F3C_SKILL_ROOT" \
bash "$SKILL_BOOTSTRAP" skill
test -f "$PWF_F3C_SKILL_ROOT/SKILL.md"
printf 'PWF_F3C_SKILL_BOOTSTRAP=PASS\n'

BACKUP_ROOT="$PWF_F3C_CODEX_HOME/backups/planning-with-files-hooks"

node "$ACCEPTED_PACKAGE/install.js" install "${COMMON_ARGS[@]}"
node "$ACCEPTED_PACKAGE/install.js" doctor "${COMMON_ARGS[@]}"

if test "$FINAL_ROLE" = current; then
  node "$CURRENT_PACKAGE/install.js" install "${COMMON_ARGS[@]}"
  node "$CURRENT_PACKAGE/install.js" doctor "${COMMON_ARGS[@]}"
  EXPECTED_INSTALLED_VERSION='0.4.0-dev'
else
  EXPECTED_INSTALLED_VERSION='0.3.5'
fi

INSTALLED_MANIFEST="$PWF_F3C_CODEX_HOME/hooks/planning-with-files/installed-manifest.json"
INSTALLED_VERSION="$(python3 - "$INSTALLED_MANIFEST" <<'PY'

print(json.loads(pathlib.Path(sys.argv[1]).read_text(encoding='utf-8'))['installer_version'])
PY
```

setup/maintenance 是有意的 installed-state transaction，但不得写 workspace。必须持续轮询异步命令，直到工具返回明确
`exit_code`；没有最终 exit code 时只能报告 `INCOMPLETE/UNKNOWN`。

这里故意调用 bootstrap 的 `skill`，不是 `all`：`skill` 只从 frozen upstream URL下载、校验并安装 pristine Skill；`all`
还会提前安装 current Managed Hooks，破坏后续“由第 5 节 transaction负责 current install/uninstall”的证据顺序。Skill
安装不等于 Hook rollback；真正的 installed-role切换仍从第一个 `node "$CURRENT_PACKAGE/install.js" install` 开始。

本 block必须作为 Cloud setup/maintenance transaction在本轮第一条模型提示词之前完成。若先启动模型，再让模型“阅读并
执行第 5 节”，即使 transaction最终 exit code 0，也只能证明 transaction本身；该 task的 `SessionStart source=startup`
早已发生，不能冒充安装完成后的 Fresh Host证据。此时应保留诊断输出、停止该 task，并在修正后的新 task中把本 block配置
为 setup/maintenance script后从头执行。

<a name="f3c-cloud-order"></a>

## 6. 四轮固定顺序

每轮只使用一种顺序：

1. 从对应 exact disarm HEAD 创建新的 Cloud task，并设置本轮 `PWF_F3C_STAGE`。
2. 等 setup/maintenance transaction 返回最终 `exit_code=0`。
3. 发送第 7 节第一条无工具提示词，保存真实 startup/UserPrompt Host 输出。
4. Resume 同一 task，发送第 7 节 Resume 提示词，保存真实 resume/UserPrompt 输出。
5. 运行第 8 节唯一只读 verifier，取得最终 `exit_code=0`。
6. 按第 9 节生成一份 `/tmp` evidence JSON 并用 checkpoint helper 校验。
7. 停止该 task；下一 stage 使用新的 exact checkout，不沿用 shell/cache 来证明身份。

<a name="f3c-stop-and-handoff"></a>

## 10. 停止条件与交接

以下任一情况立即停止并报告 `INCOMPLETE/FAIL`：

- workspace 不是 exact disarm HEAD、worktree 不干净或 activation 仍存在；
- current/accepted source、ZIP SHA、package version 或 installed manifest role不匹配；
- v0.3.5 direct-over-current 没有拒绝，或拒绝造成 backup/runtime/requirements mutation；
- rollback 未经过 current-owned uninstall，或 recovery 未经过 exact accepted predecessor；
- smart/autonomous 任一轮实际 profile不是 legacy，nonce/Plan-SHA/ledger renderer错误进入 context，或 activation 复活；
- doctor不健康、snapshot residue非零、Fresh/UserPrompt/real Resume缺失；
- 长命令没有明确最终 exit code。异步工具返回 session id时必须持续轮询；不得根据部分 stdout 判断成败。

F3C1 完成只允许进入维护者另行授权的 F3C2 smart live。F3C2 PASS 不自动授权 F3C3；两者都 PASS 后仍要单独进入
F3C4 aggregate closure。本手册不授权 ref mutation、Release、publication、promotion 或 Phase 9。
