> 让维护者可以在全新 Cloud 环境验证 Fresh、canonical planning、long tail、real Resume 与 doctor。

> 当前状态：`CLOUD-HARD-ACCEPTANCE-PASS`；Source/Candidate 与 Published Release 两步 Cloud
> acceptance 已在相互独立的 Fresh 环境中分别 PASS。
> 本文不授权 GitHub `Latest` 或 production rollback promotion。

## 0. 执行路线

R4 immutable publication 与公开下载复核已经 PASS；R5 已按以下顺序完成两条通道。下表和后续命令
继续作为精确身份的历史证据与重放路线；新的重放或晋级仍须由活动 gate 另行授权。

| 顺序/通道 | 身份与用途 | v0.3.2 当前状态 |
|---|---|---|
| 第一步 `R5-SC` Source/Candidate | 选择开发/验证分支，但把 PASS 绑定到运行时记录的精确 commit；从源码运行 Linux 回归、双构建/check ZIP，并用显式本地 `HOOKS_URL`/`HOOKS_SHA256` override 安装 | `PASS`；精确 source commit `232ccd6ec71dad35ab91d69ab7e4b4cb3b7ca1bd` |
| 第二步 `R5-PR` Published Release | 固定 immutable tag/source，从公开 Release URL 下载并校验 bootstrap，让公开 bootstrap 使用自身默认 URL 下载、校验并安装固定 ZIP | `PASS`；绑定 `v0.3.2` 与固定公开双资产 |

分支只是 Source/Candidate runbook 的运输入口，不是验收身份；该通道的 PASS 只属于运行时输出的完整
commit SHA 和由它构建的 ZIP。Published Release PASS 只属于精确 `v0.3.2` tag、公开 bootstrap/ZIP
字节、URL 与 checksum，不能由分支 checkout 中的同名 bootstrap 代替。

两条通道不得共用容器、安装状态或 B～F 结果，也不得把 Source/Candidate 的本地 ZIP override 与
Published Release 的公开 bootstrap 拼成一次执行。具体顺序：

1. 新建或 Reset cache 的 Node 22 Cloud 环境，运行第 4 节；必须看到
   `V032_SOURCE_CANDIDATE_SETUP=PASS`，随后在新 task 完成第 6～9、10.1 节。
2. 保存第一步完整原始输出并退出该环境；不要把安装后的 `/opt/codex` 复用于第二步。
3. 再新建或 Reset cache 一个 Node 22 Cloud 环境，只运行第 5 节；必须看到
   `V032_PUBLIC_RELEASE_SETUP=PASS`，随后在新 task 从头重跑第 6～9、10.2 节。
4. 按第 11 节分别回传两套摘要。任一步失败立即停止，不 repair 掩盖失败。
5. 即使两步全部 PASS，也只回传证据，不自行提升 `Latest` 或 rollback。

setup 的 direct adapter/doctor 只证明静态安装链健康，不是 Runtime 自动注入的黑盒证据。B～E 必须在
setup 结束后由新的 agent/task 验证。

## 2. 硬停止条件

遇到任一情况立即停止并保存完整输出：

- Release/重新下载字段与第 1 节精确 identity 不一致；
- tag/source、Release URL、ZIP/bootstrap filename、size 或 SHA 之间不一致；
- GitHub Release 不是 exact `v0.3.2`，或资产不是恰好一个 ZIP 加一个外部 bootstrap；
- Node major 不是 22，或环境复用了已有 `/opt/codex/hooks/planning-with-files`；
- bootstrap、doctor、Managed policy、pristine Skill 或 installed inventory 校验失败；
- B～E 缺少生成回复前的 Runtime 自动注入证据；
- real Resume 没有 catch-up、tail marker、canonical plan，或顺序错误；
- post-resume doctor 不健康、可 repair、存在 error/blocker、inventory 漂移或 snapshot residue。

失败后不得修改/覆盖同一 tag 或资产，不得放宽断言、手工执行 adapter 伪造黑盒输出，也不得 repair 后
继续计为同一次 PASS。任何字节修复都使用新身份并重新开始 seal/publication/Cloud gate。

如果第一步失败，不得继续第二步；如果第二步失败，不得用第一步的 B～F 或本地 ZIP 证明公开 Release
成立。任一通道因失败而修复后，都必须以新的精确身份从该通道 Fresh setup 开始。

## 4. Source/Candidate setup：源码回归、构建与本地安装（R5-SC）

> **第一步：** 只在全新、可丢弃的 Node 22 Cloud 环境运行。Cloud 可以通过分支运输 runbook，但
> 证据身份必须是脚本输出的完整 `RUNBOOK_HEAD`。本通道从当前 checkout 构建 ZIP，并用显式
> `file://` URL 和运行时计算的 SHA override 安装；不得把默认公开 URL 的成功算入本步。
>
> Codex Cloud 的 Source/Candidate checkout 可能是没有 remote 或本地 tag 的合成分支。这里运行
> tagless-compatible portable suite，并显式排除依赖 immutable refs/history 的
> `published-release-oracles.test.js`；该 oracle 已在 R3/R4 的 ref-aware publication audit 中 PASS，
> 仍由默认完整 `npm test` 保留，不能通过在 Cloud 补造 tag 来重放。

readonly TARGET_CODEX_HOME="${CODEX_HOME:-/opt/codex}"

trap 'rm -rf -- "$PROBE_DIR"' EXIT

readonly RUNBOOK_HEAD="$(git rev-parse HEAD)"
printf 'RUNBOOK_BRANCH=%s\n' "$(git branch --show-current)"
printf 'RUNBOOK_HEAD=%s\n' "$RUNBOOK_HEAD"

git diff --check

test "$(python3 -c 'import json; print(json.load(open("package.json", encoding="utf-8"))["version"])')" = "0.3.2"
test "$(node -p 'process.versions.node.split(".")[0]')" = "22"
grep -Fq 'HOOKS_SHA256:-b42aecafaba650e5595acef8c138d142747da38dde04fa78bfb0a7f4235e5081' \
  init-cloud-sandbox-v0.3.2.bash

python3 tools/import_upstream_runtime.py check
python3 - <<'PY'
from pathlib import Path

for value in (
    "hooks/hook_adapter.py",
    "runtime/owned-plan.py",
    "runtime/owned-catchup.py",

    path = Path(value)
    compile(path.read_text(encoding="utf-8"), str(path), "exec")

readonly PUBLICATION_ORACLE_SUITE="tests/published-release-oracles.test.js"

  find tests -maxdepth 1 -type f -name '*.test.js' \
    ! -name 'published-release-oracles.test.js' -print | sort

node --test --test-reporter=tap "${TEST_FILES[@]}" | tee "$TEST_OUTPUT"

grep -Eq '^# skipped 0$' "$TEST_OUTPUT"

printf '%s\n' "${EXECUTABLES[@]}" | grep -Fxq 'runtime/upstream/ledger-summary.sh'

ZIP_B="$PROBE_DIR/candidate-b.zip"

python3 tools/build_release.py check --archive "$ZIP_A"
python3 tools/build_release.py build --output "$ZIP_B"
python3 tools/build_release.py check --archive "$ZIP_B"
cmp "$ZIP_A" "$ZIP_B"
test "$(unzip -Z1 "$ZIP_A" | wc -l)" -eq 23
test "$(wc -c < "$ZIP_A")" -eq 82627

test "$ACTUAL_ZIP_SHA256" = "$EXPECTED_ZIP_SHA256"
unzip -Z1 "$ZIP_A" | grep -Fxq 'pwf-codex-cloud-hooks/patches/patch_planning_skill.py'

trap 'rm -rf -- "$ACCEPT_DIR"' EXIT
BOOTSTRAP="$ACCEPT_DIR/init-cloud-sandbox-v0.3.2.bash"

curl --fail --location --proto '=https' --tlsv1.2 \
  --output "$BOOTSTRAP" "$BOOTSTRAP_URL"
printf '%s  %s\n' "$BOOTSTRAP_SHA256" "$BOOTSTRAP" | sha256sum --check --strict
