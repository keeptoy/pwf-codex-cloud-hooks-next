# v0.3.4 Cloud hard acceptance

本文件只保存 v0.3.4 已经完成的版本增量与不可变 Cloud 证据。稳定执行协议、黑盒提示词、停止条件和
evidence schema 只见 [`Cloud hard acceptance template`](cloud-hard-acceptance-template.md)；本文件不复制模板
脚本，也不登记尚未完成通道的施工进度。

Source/Candidate Cloud hard acceptance 已在下述 exact checkout 上完成：当时 development bootstrap 使用
64 位 zero hash 并 fail closed，只通过 candidate ZIP 的 `file://` URL 与 SHA-256 显式 override 安装。后续
machine identity 收敛、seal 与 publication 都不会追溯改变这条证据的输入边界；本节的 Source/Candidate
结果不能证明 tag、公开 Release 资产、Published Release Cloud 或 promotion。

<a name="v0-3-4-acceptance-scope"></a>

## 1. 本版本验收增量

本版本没有改变 B～E 可观察行为：events、canary、plan-first、可选 catch-up、planning context 与 Resume source
合同均保持不变。额外需要证明的是 source/install authority 已收敛：

```text
upstream-manifest schema 2
  -> 固定 runtime bundle path + raw SHA
  -> importer / installer 严格解析同一 bundle inventory
  -> installed-manifest 保存安装快照
  -> doctor 比较当前 bundle authority、installed snapshot 与磁盘实际文件
```

本次验收增量没有改写 B～E 黑盒提示词，而是把新增供应链风险落实到模板的两个稳定检查点：

| 新增风险/合同变化 | 验收落点 | 完成证据 |
|---|---|---|
| manifest 不再保存重复 runtime inventory，两个 consumer 必须先信任同一 bundle | 模板 [`4.1 Source/Candidate setup`](cloud-hard-acceptance-template.md#source-candidate-setup) 验证 schema 2 exact keys、退休 mirrors 不再出现、manifest → bundle 原始 SHA 与严格非法输入拒绝 | `MANIFEST_BUNDLE_AUTHORITY=PASS`；portable suite 120 pass、0 fail、0 skip |
| 安装后不能只证明 snapshot 自洽，还必须证明它来自当前 bundle authority | 模板 [`9.1 Source/Candidate deep check`](cloud-hard-acceptance-template.md#source-candidate-deep-check) 比较 bundle-derived inventory、`installed-manifest.runtime_files` 与磁盘实际 inventory | `BUNDLE_INSTALLED_INVENTORY=AUTHORITATIVE`；10 项 installed runtime；0 snapshot leftovers |
| 历史 Phase 标签退休后仍须阻止未准入文件混入当前 runtime | 4.1 的 exact current id/source inventory guard 与 portable negative suite | authority check 与 portable suite 同时通过 |

因此，这一节只说明“为什么新增验证、模板改了哪里、由什么结果证明”，不复制模板脚本。exact current
id/source inventory guard 继续阻止未准入 Phase 4 文件进入 bundle；本证据不授予 Product Phase 4。
