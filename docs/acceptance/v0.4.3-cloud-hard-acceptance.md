# v0.4.3 Cloud hard acceptance

本文件是single-Discovery `v0.4.3`的Release operator guide。它编排Source/Candidate与Published Release两个独立通道，
Source/Candidate已经真实PASS，第一轮source-candidate closeout retirement checkpoint已经完成且没有删除对象；
Published Release尚未运行，不能提前写为PASS。

本版本没有新增product/runtime行为。要验证的是：Phase 4文档治理与Release资产materialization delta已经收敛为可复现的
`0.4.3`候选，exact `0.4.2` predecessor仍可进入未改变的installed runtime，正式发布后公开下载字节与
Source/Candidate实际验收字节一致。

```text
candidate admission preflight（COMPLETE；只读、不删除）
  → C0 / Source-Candidate candidate（本地冻结完成）
  → Source/Candidate Cloud（PASS）
  → source-candidate closeout retirement checkpoint（COMPLETE；全部KEEP）
  → C1 / channel checkpoint与第一退役证据（本地状态写回）
  → tag精确指向C0并完成immutable publication
  → Published Release Cloud（PENDING）
  → GitHub Release Latest promotion confirmation
  → role-window closeout checkpoint
  → C2 / final Post-run与programme closeout
```

本guide不创建standing Phase 9，也不授权维护者之外的远端写操作。宏观顺序只读
[`ROADMAP`的Release四步与C0/C1/C2](../../ROADMAP.md#release-four-step-flow)和
[`ROADMAP`的两个retirement checkpoint](../../ROADMAP.md#version-train-two-retirement-reviews)；Latest判断只读
[`GitHub Release Latest promotion confirmation`](../../ROADMAP.md#github-release-latest-promotion-confirmation)。

## 1. 定位与验收 claim

- 版本列车：`v0.4.3` documentation-governance patch candidate；继续归属Product Phase 4，不激活Product Phase 5。
- Discovery claim：history/overview/environment authority与Release资产materialization治理可以作为stable patch交付，同时保持
  v0.4.2已接受行为、exact predecessor admission与public download identity闭合。
- Source/Candidate证明final source、portable Linux suite、deterministic ZIP、override安装和真实Resume lifecycle。
- Published Release证明immutable bootstrap/ZIP默认下载链、Fresh startup与公开字节deep check。
- 任一PASS都不自动授权publication、Latest、下一Product Phase或production/runtime扩面。

## 3. 执行教程

### 3.1 本地与维护者push preflight

智能体完成完整本地回归、Release双构建和C0 commit后交接`SOURCE_CANDIDATE_HEAD`。维护者执行：

```powershell
git status --short --branch
$expectedHead = (git rev-parse HEAD).Trim()
if (git status --porcelain) { throw "v0.4.3 Source/Candidate blocked: worktree is not clean" }
git push -u origin 0.4.3
$remoteLine = git ls-remote origin refs/heads/0.4.3
if (-not $remoteLine) { throw "v0.4.3 remote branch was not found" }
$remoteHead = ($remoteLine -split '\s+')[0]
if ($remoteHead -ne $expectedHead) { throw "v0.4.3 HEAD mismatch: local=$expectedHead remote=$remoteHead" }
"SOURCE_CANDIDATE_HEAD=$expectedHead"
```

远端写入由维护者负责。此时不得创建tag、Pre-release、上传资产或把zero-hash bootstrap当作公开安装入口。

### 3.2 Source/Candidate Cloud

在全新disposable Cloud environment选择已push的exact `0.4.3` checkout。每个新task先附
[`Cloud task验收权限前缀`](../cloud-hard-acceptance-template.md#cloud-task-acceptance-permission-prefix)，再按下表执行；
不得复制旧聊天或历史guide中的脚本。

| 顺序 | 操作 | 唯一协议来源 | 必须回传 |
|---|---|---|---|
| A | 新setup task执行4.1 | [`Source/Candidate setup`](../cloud-hard-acceptance-template.md#source-candidate-setup) | 最终exit code、HEAD、portable Linux TAP、双ZIP identity、install/doctor与`PWF_SOURCE_CANDIDATE_SETUP=PASS` |
| B | A PASS后新task执行5.1 | [`post-install Resume`](../cloud-hard-acceptance-template.md#blackbox-post-install-resume) | 原始回复与真实SessionStart source |
| C | B同task执行第6节 | [`canonical baseline`](../cloud-hard-acceptance-template.md#blackbox-canonical-baseline) | exact plan ID与acknowledgment；唯一允许的workspace改动 |
| D | 同task执行第7节 | [`canonical context`](../cloud-hard-acceptance-template.md#blackbox-canonical-context) | 八项原始观察 |
| E1/E2 | 同task执行8.1后，从UI Resume同一task执行8.2 | [`real Resume`](../cloud-hard-acceptance-template.md#blackbox-real-resume) | acknowledgment、catch-up、tail、真实Resume source与顺序 |
| F | E2同一resumed task重新提取当前模板9.1 | [`Source/Candidate deep check`](../cloud-hard-acceptance-template.md#source-candidate-deep-check) | 最终exit code、HEAD、doctor、inventory、policy、residue与`PWF_SC_POST_RESUME=PASS` |

A/F HEAD必须等于交接的`SOURCE_CANDIDATE_HEAD`。C产生的`.planning` fixture不提交，通道完成后丢弃环境。

### 3.3 Source/Candidate通过后的停止点

维护者带回完整原始证据后，智能体核对真实PASS，再执行source-candidate closeout retirement checkpoint。第一轮只对
Release-excluded planning、临时教程和脚手架提出`RETIRE/MIGRATE/KEEP`；planning删除仍需维护者按
[`Planning生命周期`](../repository-governance-guide.md#planning-lifecycle)明确决定。随后把channel checkpoint与第一退役结论写回
C1 `SOURCE_CANDIDATE_CHECKPOINT_HEAD`。正式`v0.4.3` tag必须精确指向C0 `SOURCE_CANDIDATE_HEAD`，不能指向C1。

若拟清退对象会改变package、contract、runtime、bootstrap、ZIP allowlist或其他C0 Release输入，立即停止：必须形成新C0并
重新运行Source/Candidate。C1 push后才由维护者创建immutable Pre-release并上传正式ZIP与ZIP外bootstrap。

本通道必须使用另一套Fresh Cloud，只验证公开默认下载链，不设置`HOOKS_URL`、`HOOKS_SHA256`或ZIP override。publication后先把

| B | setup后的首个task执行5.2 | [`Fresh startup`](../cloud-hard-acceptance-template.md#blackbox-fresh-startup) | 原始回复、events与startup source |
| C～E | 同一task按第6～8节执行，并从UI Resume同一task | [`canonical baseline与real Resume`](../cloud-hard-acceptance-template.md#blackbox-canonical-baseline) | plan ID、八项观察、tail、catch-up与真实Resume source |
| F | E2后重新取得模板9.2，只替换新写入的ZIP URL/SHA | [`Published Release deep check`](../cloud-hard-acceptance-template.md#published-release-deep-check) | 最终exit code、公开ZIP重下载、doctor、inventory、policy、residue与`PWF_PUBLIC_POST_RESUME=PASS` |

## 4. 证据与停止条件

共同硬停止以[`模板第2节`](../cloud-hard-acceptance-template.md#acceptance-hard-stops)为准，并增加：

- production、runtime bundle、Host ABI、managed events或adapter-only policy相对v0.4.2发生非预期变化；
- transition不是exact v0.4.2 predecessor，或候选宣称支持未列入contract的旧installed state；
- 任一文档把未运行通道写成PASS，或provenance提前出现未发布v0.4.3身份；
- Source/Candidate前bootstrap含non-zero默认ZIP SHA，或publication后重新打包却沿用原tag/资产身份；
- Cloud模型修改候选、commit/push、创建PR/Release，或没有取得真实最终exit code。

维护者回传必须保留A/F完整stdout/stderr和exit code、portable suite摘要、ZIP entries/size/SHA、B～E原始回复、doctor JSON、
inventory/policy/residue及首次失败输出。失败后若环境或候选字节改变，必须Fresh重跑对应通道。
