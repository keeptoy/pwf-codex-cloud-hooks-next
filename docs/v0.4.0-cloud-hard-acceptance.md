## P9-B sealed-source Cloud 操作入口

本节回答“维护者现在具体怎么验收”，但不保存第二份 Bash 权威。长脚本和通用黑盒提示词始终从最终 checkout 的
[`Cloud hard acceptance template`](cloud-hard-acceptance-template.md#source-candidate-sequence) 读取；不要使用旧 `/tmp` 副本、
旧分支文档或聊天记录里的脚本。以下所有 `__PWF_P9B_EXPECTED_HEAD__` 都必须替换为第 1 步打印的真实 commit。

### 1. 本地确定、push 并核对 exact HEAD

先确认本地 `0.4.0` 工作树干净，再由维护者执行下面的 PowerShell。智能体不得代替维护者 push：

~~~powershell
git status --short --branch
$expectedHead = (git rev-parse HEAD).Trim()
if (git status --porcelain) { throw "P9-B push blocked: worktree is not clean" }
git push origin 0.4.0
$remoteLine = git ls-remote origin refs/heads/0.4.0
if (-not $remoteLine) { throw "P9-B remote branch was not found" }
$remoteHead = ($remoteLine -split '\s+')[0]
if ($remoteHead -ne $expectedHead) {
  throw "P9-B HEAD mismatch: local=$expectedHead remote=$remoteHead"
}
"PWF_P9B_EXPECTED_HEAD=$expectedHead"
~~~

最后一行就是本轮唯一允许使用的 sealed-source HEAD。文档中的旧 commit、P9-A 起点或先前 Cloud HEAD 都不能替代它。

### 2. 准备正式 Cloud 环境

在 Codex Cloud 环境设置中选择本仓库与 `0.4.0` 分支，并把实际 Node major 以纯数字环境变量
`PWF_ACCEPTANCE_NODE_MAJOR` 注入。若不知道该环境的 Node major，可先在一次 disposable fact-only task 中运行
`node -p "process.versions.node.split('.')[0]"`；取得数字后丢弃该 task，设置变量，再新建正式 Fresh task。探针结果不是
P9-B evidence，正式验收不能从探针会话续跑。

每个新 Cloud task 的第一条消息都要先附通用模板第 0.4 节的“Cloud task 验收权限前缀”，明确禁止自动修复、commit、push
和 PR。异步工具只返回 `session_id` 时必须继续轮询；没有明确最终 `exit_code` 只能报告 `INCOMPLETE/UNKNOWN`，不得猜 PASS
或 FAIL。

### 3. 第一轮运行 4.1 Source/Candidate setup

创建正式 Fresh Cloud task，把 `__PWF_P9B_EXPECTED_HEAD__` 替换后发送下列文字；实际 Bash 只能从
[`4.1 Source/Candidate setup`](cloud-hard-acceptance-template.md#source-candidate-setup) 提取：

本轮 P9-B expected sealed-source HEAD 是 __PWF_P9B_EXPECTED_HEAD__。
