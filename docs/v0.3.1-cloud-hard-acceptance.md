> 目的：让第一次接手本仓库的维护者，可以在一个全新的 Codex Cloud 沙箱中，直接完成
> `0.3.1` 安全修复候选的 Linux、setup、Fresh lifecycle、canonical planning、真实 Resume
> catch-up、doctor、inventory 与 residue 验证。
>
> 当前状态：`S2 PENDING CLOUD`。本文不是 Release 证明，不能创建 tag、发布资产、写入最终 ZIP
> hash 或提升 rollback。accepted rollback 仍是不可变 `v0.3.0`；beta.2 仍是 previous fallback。

## 0. 新人快速路线

1. 在 Codex Cloud 环境中选择 Node 22。
2. 选择分支 `validation/v0.3.1-s2-runbook`，创建全新容器，不复用生产环境。
3. 把第 3 节脚本作为 setup script；确认结尾出现
   `V031_S2_DISPOSABLE_SETUP=PASS`。
4. setup 完成后创建一个完全新的 task，依次原样发送 B、C、D、E1、E2 提示词。
5. E2 PASS 后执行 F；保存原始输出，不要只保存人工总结。
6. 把第 11 节证据表填好并交回维护者。任一步失败立即停止，不 repair 掩盖失败，也不进入 S3。

setup 中的 direct adapter probe 只证明安装后的静态调用链可执行，不是 Runtime 自动注入的黑盒
证据。B 必须在 setup 结束后创建的全新 task 中验证。

## 2. 硬停止条件

遇到任一情况立即停止并保存输出：

- runbook 分支不包含 exact candidate，或除允许的 evidence-only 路径外还有其他差异；
- 工作树在 setup 入口不干净；
- Node major 不是 22；
- Linux suite 有任意 failure 或 skip；
- ZIP entry、size、hash、双构建或 extracted importer 不一致；
- 发现当前沙箱已有 `/opt/codex/hooks/planning-with-files`，说明不是 Fresh setup；
- bootstrap、doctor、Managed policy 或 pristine Skill 校验失败；
- B～F 任一步缺少必需 Runtime 自动注入证据；
- post-resume doctor 不健康、可 repair、存在 blocker/error、inventory 不一致或有 snapshot residue。

失败后不得修改候选、放宽断言、手工执行 adapter 伪造黑盒结果、repair 后继续计为同一次 PASS，或把
Windows skip 当作 Linux 证据。修复必须回到新的授权 gate，并重新开始一次 Fresh Cloud 验证。
